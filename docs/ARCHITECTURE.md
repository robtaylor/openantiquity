# Architecture

This is the build contract. `docs/DESIGN.md` says what the product does and why. This file says how the code is laid out, what the tables are, and what the API looks like. If code and this file disagree, fix one of them in the same change.

The product is called "OpenAntiquity". The Python package, database and cookie prefix are all `fieldclub`.

## Stack

| Part | Choice |
|------|--------|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (sync) on psycopg 3, GeoAlchemy2, Pydantic 2 |
| Database | PostgreSQL 17 with PostGIS 3.5, `pg_trgm`, `citext` |
| Terrain | numpy, scipy, rasterio. Tiles are rendered on demand and cached |
| Frontend | TypeScript (strict), React 19, Vite, MapLibre GL JS 6, TanStack Query, Zustand |
| Tests | pytest against a real PostGIS, Vitest, Playwright for end-to-end |
| Deploy | One container, PostgreSQL and a bucket with the S3 interface: Fly Machines in London, Fly Managed Postgres 17 and Tigris, described by `fly.toml`, `infra/fly/` and tested scripts in `infra/` (Decision 0018, `infra/README.md`). The Google Cloud deployment in `infra/terraform` stays until the cut-over. The application speaks S3 only, not Cloud Storage |

Endpoints are plain `def` functions. FastAPI runs them in its thread pool, which suits a workload of SQL, upstream HTTP and numpy. Only the event stream and the terrain tiles are `async`: the tiles are drawn on threads of their own (`terrain/workers.py`), so a flood of them can't take the pool everything else runs on. See Decisions 0001 and 0015 in `docs/architecture/decisions/`.

## Conventions

- The product is called OpenAntiquity wherever a person outside can see it: the interface, the API's text and reference, emails, the `User-Agent`, download names, the cookies and the `X-OpenAntiquity-Client` header, and these docs. In the code and the cloud it is `fieldclub`: the package, the `FIELDCLUB_*` settings, the commands, the browser storage keys and every cloud resource. The two are the same thing (Decision 0017). Both names are reserved as handles and display names.
- Database access goes through SQLAlchemy sessions from `get_db`. Write explicit `select()` statements. Don't rely on lazy-loaded relationships.
- Services take a `Session` and plain values, and return models or dataclasses. Routers translate between HTTP and services. Services never import FastAPI.
- Every error raised on purpose is a subclass of `AppError` with a stable `code`. The handler returns `{"error": {"code": ..., "message": ...}}`. An error raised by one module is defined there. An error raised by more than one module lives in `errors.py`, or in its package's own errors module (`terrain/errors.py`, `ingest/errors.py`, `auth/failures.py`), and the module it first lived in imports it back so old imports keep working. A router defines none.
- A response model takes an `Out` suffix only when it would otherwise share a name with a type the code already uses: a model, a service or vocabulary type, another schema, or a library type such as shapely's `Point`. So `RecordOut` and `SourceOut` beside the `Record` and `Source` models, but `LiveSource`, `Location` and `GeoPoint`. A renamed model renames the generated client's type, so `pnpm gen:api` follows it.
- Enumerations are `StrEnum` classes in `vocab.py`, stored as `TEXT`. No native PostgreSQL enums.
- A version passes over an activity kind or a next step it has no name for (`feed._listed`, `confidence._known_steps`, Decision 0033). A deploy changes the schema before it swaps the machines, so an earlier version meets what a later one stored. A new value in any other stored vocabulary takes a new `ASSESSMENT_VERSION` or a deploy of its own first.
- A version reads a stored feature class it has no name for as `unknown`, "Not sure" (`vocab.stored_class`, Decision 0035). Every reader of a finding's or a second look's class goes through it, and a response field that carries a class is typed `ShownClass` (`schemas/common.py`), which does the same. `tests/test_stored_class_is_never_read_strictly.py` fails on a strict read. "Not sure" sent back in an edit or a note for such a class leaves the stored class alone. The interface shows a class id its `/meta` doesn't list as "Not sure" (`shownClass` and `classLabel` in `features/finding/describe.ts`).
- The schema step widens a vocabulary's check and never narrows one, except for a value named in `_DROPPED_VALUES` in `db.py` (`_sync_enum_checks`, Decision 0035). A check that admits a value this version has no name for is left alone, so an earlier image gone back to doesn't refuse what a later one stored.
- Primary keys are `BIGINT` identity columns. Public URLs use `findings.public_id`, `investigations.public_id` and `users.handle`, never raw ids.
- All geometry is stored in EPSG:4326. Distance queries cast to `geography`. The functional indexes below make those casts indexable.
- Timestamps are `timestamptz` and always UTC.
- There's no migration history. Every deploy runs `fieldclub-release` (`release.py`, the `release_command` in `fly.toml`) once, before any machine is replaced. It runs `fieldclub-terrain check` first and stops, with the schema untouched, when that fails. Then it runs `python -m fieldclub.db`, whose `create_schema()` creates what the database lacks from the models plus `models/extras.sql`, on the live database while the old version still serves. It works in one transaction under an advisory lock, and each wait for a lock on a table is limited to `SCHEMA_LOCK_TIMEOUT_MS`, 5 seconds. A longer wait fails the run, and the transaction changes nothing. Every `ALTER TABLE` in `extras.sql` that adds columns runs only when `fieldclub_has_columns` finds one of them missing. A vocabulary check whose values differ from its enumeration's is dropped and added again `NOT VALID`, which scans no rows, and a second transaction validates it, which lets reads and writes go on.
- Logging uses the `logging` module. No `print` outside the CLIs.
- Outbound HTTP uses the shared `httpx.Client` from `fieldclub.http`, which sets a timeout and a `User-Agent` naming the project.
- Assert assumptions. A wrong assumption about an upstream payload should fail loudly in ingest, not write bad rows.

`sources.reuse` classes each source by what its licence allows, per Decision 0004. OpenAntiquity is non-commercial, so `non_commercial` sources are ingested. Exports carry the licence per record.

`sources.access` follows Decision 0007. A `bulk` source is stored in `records`. A `live` source is queried by the browser when someone looks at an area and is never stored on our servers. A `deeplink` source is only linked. A finding linked to a live or deep-link record stores the record's identifier and address in the evidence row and nothing else. Evidence linking a stored record keeps its identifier (`reference`), address (`url`) and source key as well as `record_id`, so when a full ingest removes the record and `record_id` is emptied, the evidence stays a working reference.

`records.category` is one of `designation`, `monument`, `find`, `event`, `document`, `community`, `map_label`. It drives map layers and filters. `precision_m` records how exact the position is. A Portable Antiquities find published to a 1 km square has `precision_m = 1000`. The `map_label` records are the antiquities lettered on the Ordnance Survey six-inch maps of about 1900, from the GB1900 gazetteer, under its share-alike licence.

<!-- Investigations and squares (track b2/investigations). -->
Anyone with an investigation's id can read a public or unlisted one; a private one is found only by its owner, and everyone else gets `investigation_not_found`. The owner and editors change the title, summary, notes, area and items. Only the owner changes visibility, members and deletes it, and any other member can leave. The owner invites a contributor by handle; someone who hasn't finished the welcome step can't be invited. An invited person has no role, and the investigation isn't in their `mine` list, until they accept with `POST .../invitation`. They decline by leaving, which needs only a session. Inviting someone sends them an `investigation_invitation` notification naming only the owner and the investigation's public id, never its title or any other free text (Decision 0009), and nothing reaches the feed or the event stream. It leaves their list once they decline or the owner takes it back. Only public investigations are in the public list. `scope=invited` lists a person's waiting invitations, and `scope=unlisted` lists every unlisted investigation for moderators only, so collaborators never share a notebook moderators can't find (Decision 0009, rule 5). Anyone who can read an investigation can report it, and a moderator can hide it: a hidden investigation is found only by its members and moderators, carries `hidden: true` for them, and leaves the public list, the invitations list and feeds. Making one public records `investigation_published`, and making it unlisted or private deletes that row. Every change takes the investigation's row lock first, so membership and visibility can't race, and `investigation_items` has a deferred unique constraint on `(investigation_id, position)`. An item pointing at a withdrawn finding or a record no longer in the index is returned with `unavailable` set to `withdrawn` or `gone` and nothing of the target. So is one pointing at a hidden finding, with `hidden`, for anyone but the finder and moderators. Exports follow the download rule of Decision 0005 and leave such items out; the report is one HTML page with no scripts, served with a sandboxing `Content-Security-Policy`. It reads the notes and each item's note with the notebook's part of Markdown (`services/notes_markdown.py`): headings, paragraphs, lists, strong, emphasis and links to http and https addresses, everything else escaped, and the work bounded by the note's length. A note whose markup would join figures into a position the text as typed doesn't hold is shown as written. When an account is deleted its private investigations are deleted with it, each shared one it owns passes to its longest-standing editor, and one with no editor stays readable with nobody able to manage it. Its memberships and invitations elsewhere go.

A square survey counts towards coverage unless its result is `skipped`. `GET /squares/next` ranks the squares a person hasn't done near the point by how many people have had them, skips included, then by distance, and picks at random among the best eight, so people asking at once are spread out. A square has 1 m elevation to scan when the 5 km tile of `terrain/catalogue.py` that holds it is listed and its centre is inside England's boundary in `admin_areas`. The catalogue lists partial tiles at the coast and the borders, so the tile alone would hand out squares at sea or in Wales and Scotland. Nothing reads the rasters, so a coastal square whose centre is offshore is lost and one whose centre is just inland may be mostly sea. Until `admin_areas` holds England, the tile alone decides and a warning is logged. Coverage counts each result as it was given: a square stays marked after the finding marked there is hidden, withdrawn or deleted, because a survey keeps only a count of findings. It shows no more than that somebody marked something in a public 1 km square.

- `GIST (location)`, `GIST ((location::geography))`, `GIST (location_public)` and `GIST ((location_public::geography))` on `findings`. Also `GIN (open_steps)` for the help-wanted lists and `(created_at, id)` for the newest-first list.
- `GIST (geom)`, `GIST ((centroid::geography))`, `GIN (search)` and a trigram `GIN (name gin_trgm_ops)` on `records`. Also `GIST (centroid)` for the record tiles and `(lower(name) text_pattern_ops)` for names that start with the search text.
- Trigram `GIN (name gin_trgm_ops)` and `GIST (geom)` on `places`.

## Confidence engine

`services/confidence.py` exposes one pure function, `assess(inputs) -> Assessment`. It reads nothing from the database. `services/findings.py` gathers the inputs, calls it after every change to a finding's observations, evidence or votes, stores the result on the finding, and emits activity when the tier or state changes. The rules below are the specification. Thresholds live in one `Thresholds` dataclass so they can be tuned without touching logic.

### Weights

A person's weight is set by role: member 1.0, trusted 1.5, expert 3.0. Moderators and admins count as trusted. The finder's own opinion never counts towards visibility. Every contributor is a signed-in account, so there is no lower weight for anonymous input. An answer and a vote are weighed by the role their giver had when they gave it (`role_at_answer`, `role_at_vote`), and keep counting through a ban, so no later change of standing moves a score through them (Decision 0019). The finder's feature class and evidence are weighed by each person's role today.

### Quantities

- `seen` is the summed weight of other people who answered "yes, I can see it". `unseen` is the same for "no". `observers` is the number of distinct people who answered yes.
- `seen_ratio = seen / (seen + unseen)` when the denominator is positive.
- Class support sums weight per feature class over the finder's class and every observation that counts towards `seen` and names one. `unknown` is ignored. `class_agreement` is the top class's share. When agreement is at least 2/3 and total support is at least 2.0, the top class becomes `community_class`.
- An evidence item stands when its weighted vote total is not negative and it isn't deleted. A finding's page gives each item that total with the number of people who endorsed and disputed it, counted the same way. It's independent when someone other than the finder added it, or someone other than its contributor endorsed it with weight of at least 1.0.
- Strands group evidence kinds: `lidar_view` is lidar, `aerial` is aerial, `historic_map` is historic map, `record_link` (relation related or part_of) is records, `document` is literature, `photo` and `field_visit` are ground, `geophysics` and `excavation` are survey, `her_record`, `designation` and `publication` are official. The desk strands are lidar, aerial, historic map, records and literature. A strand is supporting when it has at least one standing, independent item with stance `supports`. Ground and survey items count towards the disputed and ruled-out rules below only when they are standing and independent too.
- Each check (`not_modern`, `not_natural`, `not_artefact`) is cleared when the weight of observations that count towards `seen` and assert it is at least 2.0 and more than twice the weight of observations giving the matching explanation.

### Tiers

| Tier | Label | Requires |
|------|-------|----------|
| `spotted` | Spotted | Nothing. Every finding starts here |
| `seen` | Seen by others | `seen >= 2.0`, `observers >= 2`, `seen_ratio >= 2/3` |
| `corroborated` | Corroborated | Seen, plus two supporting desk strands, plus `class_agreement >= 2/3` from at least two people |
| `probable` | Probable | Corroborated, plus all three checks cleared, plus a yes from a trusted or expert reviewer or `seen >= 7.0` |
| `ground_checked` | Checked on the ground | A standing ground or survey item with outcome `supports`, endorsed with weight 1.0 by someone else or added by a trusted or expert user. Doesn't require the earlier tiers |
| `confirmed` | On record | A standing official item verified by an expert or moderator who is neither the finder nor the item's contributor. Doesn't require the earlier tiers |

### States

A finding's state is separate from its tier.

| State | When |
|-------|------|
| `open` | Default |
| `known` | A standing `record_link` with relation `same_as` whose contributor weight plus endorsements reaches 2.0. The finding matches an existing record |
| `disputed` | `seen >= 2.0` and `unseen >= 2.0` with ratio strictly between 0.33 and 2/3, or contradicting strands at least equal supporting strands, or ground items disagree |
| `ruled_out` | `unseen >= 3.0` with ratio at most 0.33 (reason `not_visible`), or one explanation's weight is at least 3.0 and exceeds `seen` (reason is that explanation), or a standing ground item with outcome `contradicts` and none supporting (reason `ground_check`). Never applied at `ground_checked` or above |
| `withdrawn` | The finder withdrew it |

### Score and next steps

`confidence` is a 0 to 100 number for the meter. Each tier has a base: 10, 30, 50, 70, 85, 100. Progress towards the next tier adds a share of the gap in proportion to the requirements already met. A ruled-out finding scores 0.

`next_steps` lists the unmet requirements of the next tier as `{code, prompt, ...}`. Codes are `need_observers`, `need_strand`, `need_class_agreement`, `need_check`, `need_trusted_review`, `need_ground`, `need_official`. The same codes drive the help-wanted queue, so a finding's open steps are exactly the tasks offered to other people.

### Finer rules

The module docstring of `services/confidence.py` gives the reasoning for each of these.

- The finder's own observation is ignored for everything. Their class counts once, through the finding's feature class.
- Only a "yes" with no explanation counts as seeing it: towards `seen`, as an observer or a reviewer, for class support and for the checks. A "yes" that gives an explanation counts only as that explanation's weight, as every answer's explanation does.
- Votes by an item's own contributor and by the finder are ignored. Independence is required of contradicting evidence as well as supporting evidence.
- A field item points the way its `outcome` says, and `inconclusive` is neutral. Without an outcome, and for every other kind, its `stance` decides. Only independent field items count towards "ground items disagree" and the ruling-out on the ground. A finder's own field item needs someone else's endorsement to reach Checked on the ground, even when the finder is trusted.
- A verifier is an expert, moderator or admin who is neither the finder nor the item's contributor, on an official item that stands and supports.
- Every two-thirds figure is exactly 2/3. The disputed band is open at both ends, so a ratio of 2/3 is Seen. Contradicting strands make a finding disputed only when there is at least one.
- State precedence is withdrawn, ruled out, disputed, known, open. A ruled-out rule that holds at Checked on the ground or above makes the finding disputed, with that rule's reason. When several ruled-out rules hold, the reason is `ground_check`, then the heaviest explanation, then `not_visible`.
- A withdrawn finding keeps its tier, scores that tier's base and has no next steps. A ruled-out one scores 0 and has none either. The score is rounded down.

### Reputation

Points are written to `reputation_events`, so a person can see where each one came from. A finding reaching seen earns its finder 2, corroborated 5, probable 10, ground checked 20, confirmed 30. An observation that matches the outcome when a finding reaches corroborated or ruled out earns 1. An evidence item endorsed by two other people earns 1. A finding that turns out to match a known record earns 1. There are no penalties. A finding earns the points of every tier whose rule it newly meets, not only the one it lands on, and each award is paid once however often a finding drops and climbs back. A ruled-out or withdrawn finding earns nothing while it stays so. An answer matches corroborated when it counts as seeing it, and ruled out when it says "no" or gives an explanation. The two endorsers are people other than the contributor and the finder. A member who reaches 50 points becomes eligible for trusted, and a moderator makes the promotion. It isn't automatic: trusted users download protected findings' exact positions (Decision 0005), and three colluding accounts can take a finding to Checked on the ground, worth 27 points to its finder.

## API

All paths are under `/api/v1`. Bodies are JSON, at most 1 MB (`security.BODY_MAX_BYTES`): a longer body, whether it states its length or not, is refused unread with 413 `request_too_large`, and only `POST /media` takes more. The session is a `__Host-openantiquity_session` cookie, HttpOnly, Secure and SameSite=Lax, for the whole site and this host alone (`openantiquity_session`, not Secure, in local development over http). Every mutating request must carry the header `X-OpenAntiquity-Client: web`, which a cross-site form can't send. The one exemption is the exact path `POST /auth/oauth/apple/callback` (see Accounts).

Rules every route follows, whichever area it belongs to:

- Rate limits, bans and the hashed address kept with a session use the caller's address, from `auth.deps.client_ip`. When `FIELDCLUB_CLIENT_IP_HEADER` is set, the address is read from that header alone, and a request without exactly one address in it gets the socket's. On Fly the header is `Fly-Client-IP`, which Fly's proxy overwrites. The header is believed from any sender, so it is safe only because every request comes through the proxy: the service binds `0.0.0.0`, and Fly's private network, which is IPv6 and bypasses the proxy, reaches only a service bound to the machine's private address. Binding `::` or `fly-local-6pn` would let another machine in the organisation choose its own address. Otherwise the address is the `FIELDCLUB_TRUSTED_PROXY_HOPS`th entry of `X-Forwarded-For` from the right, or the socket's when that is 0. Production refuses to start with neither set, and a Fly machine refuses to start without the header.
- A request whose `Host` is one of `FIELDCLUB_REDIRECT_HOSTS`, the site's other names, is answered 308 with the same path and query on `FIELDCLUB_PUBLIC_URL`, before any route sees it, and before every middleware but the one that adds the security headers, so the redirect carries them (`redirects.py`). Any other name is served, so the platform's own address and its health checks still answer. The settings refuse a list that names the public address's own host.
- Every write is rate-limited. One that stores a contribution needs a signed-in account that has finished the welcome step, or answers `onboarding_required`. Every route has a response model, so the generated client covers it.
- Lists are paged with `limit` and an opaque `cursor`. Each list keeps its own cursor: a key for a list whose order is fixed, an offset for one whose order moves as people answer. No offset goes past 2,000. A cursor that is wrong in any way is 400 `invalid_cursor`, and a `limit` above the list's maximum is 422 `validation_error`.
- A `bbox` is `west,south,east,north` in degrees, four finite numbers with west < east and south < north. Anything else is 400 `invalid_bbox`, and `fieldclub-ingest --bbox` takes the same boxes.
- A filter with several values is a repeated parameter, `category=a&category=b`, and an unknown value is 422 `validation_error`. The record tile address is the exception: its `category` is comma-separated, because a tile address is a template.
- Every answer carries `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy: same-origin` and a `Permissions-Policy`, and over https `Strict-Transport-Security` (`security.py`). The policy allows scripts, styles and fonts from this site only, no inline script and no `eval`, the app shell's inline styles by their hash, MapLibre's workers and images from `blob:` and `data:`, map tiles and the live record sources from the hosts `/meta` and `/context/live-sources` name, video thumbnails from YouTube's and Vimeo's image hosts, and no frames or framing. A photo and the printable report send stricter policies of their own. Production serves no API docs and no `/api/openapi.json`; `fieldclub-openapi` writes the schema.
- A response that sets no cache policy of its own is sent `private, no-cache` with `Vary: Cookie`, because most answers depend on who is asking. One that sets a cookie is sent `private, no-store` whatever the route said. Only answers that are the same for everyone are publicly cacheable: tiles, the coverage layers, the context catalogue, and for five minutes (`deps.shared`) `/meta`, `GET /sources`, record search, nearby records and a record's page. `tests/test_routes.py` marks each with `public` and fails when a route's policy and its row disagree.

The map asks again: it fetches this server's terrain and height tiles through a protocol of its own (`map/patientTiles.ts`, registered where the app starts by `map/tileProtocol.ts`), which takes a 503 that names a `Retry-After` as "not yet", waits that long and a little longer each time, and tries up to 8 times within 30 seconds, stopping when the map cancels the tile. A tile that outlasts that, or fails any other way, fails as MapLibre's own fetch would have. These answers, and a remembered failure, are normal traffic: the error handler logs an `AppError` marked `expected` at INFO without a traceback, and every other 5xx at ERROR with one.

Every tile carries an ETag and answers `If-None-Match` with 304, through one helper, `api.deps.not_modified`, which the coverage layer uses too. A tile off the map is 404 `tile_not_found`. A terrain tile at a zoom outside the range it is served at is 404 `zoom_out_of_range`, while a record tile answers `tile_not_found` for any zoom outside 0 to 22. The addresses in `/meta` carry `?v=`, a token of everything that could change the tile: for terrain, the style version, the elevation format and the data editions, the national overview's build among them; for records, the tiles' format (`record_tiles.TILE_FORMAT`), the last ingest run to finish in any status, every run still going and the enabled sources. A failed run counts because the runner commits batch by batch. A tile asked for with the current token is sent as immutable, so an ingest or a new edition reaches every browser at once. A record tile is never immutable while an ingest run is going, because each batch changes it.

### Accounts

Anyone can read everything public without signing in: the map, findings, records, investigations, activity. Every write needs a session. There are no guest accounts, so every stored contribution belongs to a real account.

People can still try the tool before joining. Marking a finding, answering a second look and scanning a square all work signed out, and the result is held in the browser as a draft. Drafts never reach the server. Pressing save opens the sign-in sheet, and after sign-in the frontend submits the drafts. Drafts live in `localStorage` because the provider redirect reloads the page.

Sign-in is by provider, with no passwords. Google, Apple, Microsoft and Facebook are the main ones, and OpenStreetMap is offered too because many contributors have an account there. Each provider is enabled only when its credentials are configured. An emailed one-time link is the fallback for people who use none of them. Providers run as a server-side authorisation-code flow with `state` and PKCE. The callback verifies the identity, finds or creates the user, sets the session cookie and redirects to the `next` path it was given, which must be a relative path on this site.

The state, OpenID Connect nonce and PKCE verifier of one provider sign-in travel in `openantiquity_oauth`, an HMAC-signed, HttpOnly cookie that lasts ten minutes, is scoped to that provider's callback path and is cleared by the callback. A cookie rather than a server-side row binds the flow to the browser that started it, which stops a callback address being replayed into someone else's browser, and costs no write per click. Google, Microsoft, Apple and OpenStreetMap go through one OpenID Connect client that caches each provider's discovery document and key set, fetches the key set again when a token names an unknown key (at most once a minute), and accepts only RS256 and ES256 signatures. Facebook is plain OAuth 2 with a profile call. Apple returns with a cross-site POST that can't carry the client header, so `POST /auth/oauth/apple/callback` is the one path exempt from it, and its flow cookie is SameSite=None. A sign-in that fails at the start or the callback redirects to the `next` path with `?signin_error=` and a short code: `state_mismatch`, `invalid_token`, `provider_error`, `cancelled`, `banned`, `account_deleted`, `provider_unavailable` (a provider that isn't offered), `email_unavailable` or `signin_failed` (anything unexpected). Every sign-in issues a new session and ends any session the browser presented. Apple's cross-site POST doesn't carry the SameSite=Lax session cookie, so the flow cookie also holds the hash of the session presented at the start, and the callback ends that one too. Only Google's and Apple's verified addresses count as verified, and Microsoft's only with the domain-owner flag (`xms_edov`), because a Microsoft directory can set any address. OpenStreetMap is asked for no address, and Facebook never says one is verified, so neither links accounts. An address goes on an account only when it is verified and nobody else holds it. Addresses are CITEXT, and Postgres `lower()` folds a few non-ASCII capitals to ASCII letters (`İ` to `i`), so an address the database matches counts as the same only when the two differ in nothing but ASCII case. Otherwise a link answers `email_unavailable` and a provider identity gets an account of its own, without the address.

The `next` path must start with exactly one slash and contain no backslash, no control or invisible character and no `.` or `..` segment, in any percent-decoded form. The frontend uses a `next` it receives (from `?next=` on the link page, or the target of a `signin_error` redirect) only through same-origin router navigation, never by assigning it to `location`.

`POST /auth/email/start` stores a SHA-256 of a fresh token and emails the link for any well-formed address, without looking the address up, so the answer never says whether an account has it. Asking again from the same browser spends the links that browser asked for before for that address, so only its newest works; a stranger asking for the same address spends none of them. Three links an hour per mailbox for each caller, an IPv6 caller counted by its /48, twenty per mailbox from all callers together, counting `ann+tag@` as `ann@`, and ten per caller, so one stranger can't use up an address's budget and lock its owner out. A browser that has signed in to the mailbox by link before asks from a budget of its own, ten an hour, outside the shared twenty, so strangers on many addresses can't lock it out either: verify sets `openantiquity_email_known`, scoped like the link cookie and kept a year, holding a keyed hash of each of the last four mailboxes it signed in to. The token is in the link's fragment, so it stays out of server logs. `POST /auth/email/verify` spends it with one conditional update: a link works once, within fifteen minutes, and an unknown, spent or expired link all fail with `link_invalid`. `start` sets `openantiquity_email_link`, an HttpOnly cookie scoped to `/api/v1/auth/email` that lasts as long as the link, holding a random value whose hash is stored on the link; a browser keeps its value across asks. Verify signs in at once only when that cookie comes back. In any other browser it answers 409 `confirmation_required` with `details.email` masked (`a***@example.org`), spends nothing, and signs in only when posted again with the address the person types as `email`, which must be the one the link was sent to: another is 409 `email_mismatch`, and spends nothing either. A masked address alone can't stop someone sending their own link to a victim and signing the victim in to the sender's account, because anyone can choose an address that masks the same as the victim's. The victim types their own, which isn't the sender's. The link page must ask for the address and never fill it in. The answer is the person with `asked_here`, false when the link was asked for in another browser: the interface then saves no signed-out drafts without asking. A link that can't be sent answers 502 `mail_not_sent`. `FIELDCLUB_MAIL_BACKEND` chooses `log` (development and tests only) or `smtp`.

A first sign-in creates the user with a display name from the provider and a generated handle such as `QuietBarrow42`. A welcome sheet lets them change both. A second provider that asserts the same verified email is linked to the same user. An unverified email never links accounts.

Both project names are reserved, and nobody may pass for the project, its staff or a deleted account (`auth/handles.py`). Handles and display names are compared by their skeleton: case, width, spaces, hyphens and underscores folded away, Cyrillic and Greek letters drawn like Latin ones read as those, digits used as letters read as letters, and a number at the end set aside. A name holding either project name is refused, and so is a staff word (admin, moderator, mod, staff, system, root, official) with only generic words or a number on either side of it, so `Open-Antiquity`, `Open Antiquities`, `Admin-Team`, `Site Moderator` and `Аdmin` with a Cyrillic A are refused and `Badminton` and `Staffordshire` aren't. A name that starts like a deleted account's label (`Former member (deleted)`) is refused too. A handle given up, by a change or by deleting the account, is held back from everyone else for a year (`released_handles`, `handle_held_back`); whoever gave it up may take it back, and an account holds back only its latest three, so changing name again and again can't reserve names.

A session lasts 90 days without use (`FIELDCLUB_SESSION_DAYS`) and a year from sign-in however much it is used (`FIELDCLUB_SESSION_MAX_DAYS`). `POST /auth/logout-everywhere` ends every session the person has. `fieldclub-jobs purge-sign-ins` deletes expired sessions, and sign-in links spent or expired over a day ago.

No picture from a sign-in provider is read, stored or shown, so no page makes a visitor's browser contact a provider (Decision 0020).

Contributors must be 16 or over. The welcome sheet asks for an age band, 16 to 17 or 18 and over, and for acceptance of the contributor terms, and `POST /auth/welcome` stores both, once. Until then `age_band` and `terms_accepted_at` are empty, and every route that stores a contribution refuses with code `onboarding_required`. A bio is public free text, so it counts: `PATCH /auth/me` refuses a non-empty `bio` until the welcome step is done. Changing handle, display name or settings, and clearing a bio, stay open. An account in the 16 to 17 band shows only its handle, never a provider name, and so does an account that hasn't chosen a band. The minimum age is the setting `FIELDCLUB_MIN_AGE`, 16 to 18. At 17 or 18 only the 18-and-over band is accepted, and accounts already in a lower band are refused with `below_minimum_age`. See Decision 0009.

There is no private messaging and no private channel between members. A private investigation has exactly one member. Adding a collaborator requires making it public or unlisted, and moderators can read and list unlisted investigations. Nobody becomes a collaborator without accepting an invitation. An uploaded photo is shown to other people only after a moderator or trusted member approves it. The people who may approve photos see unapproved ones, so they can judge them, and nobody approves their own.

`POST /auth/dev-login` signs in as a named test user, through the same path as every other sign-in, so it ends the session the browser presented. `GET /auth/dev-outbox?to=` lists, newest first, the emails the log mailer sent to that address, with each sign-in link apart. Both exist only when `FIELDCLUB_ENV` is `dev` or `test` and `FIELDCLUB_DEV_LOGIN` is on, and `/meta` says so as `auth.dev_login`. They are how local development and end-to-end tests get a session.

`GET /auth/me` and `GET /auth/session` give the person's own `id`, which never changes, so the browser can tell whose drafts are whose. `PublicUser` never carries it, but it isn't secret: the moderation routes name a reported or acted-on person by it as `target.id`. `POST /findings` with a `client_ref` takes a transaction-level advisory lock on the person and the reference before looking for the finding it made, so two copies of one draft sent at once make one finding.

`DELETE /auth/me` removes the email, identities, sessions, follows, notifications and the file of every photo the person uploaded, and marks the user deleted. A photo's row goes with its file, except for a refused or hidden photo, whose row stays so that the same image stays refused to everyone, and which nobody can download any more. The files are deleted only after the deletion commits, so a failure leaves orphaned files rather than rows without one. Their contributions stay, credited to "former member", because they were published under an open licence and other people's work builds on them: findings, answers, evidence, votes, comments, mentions, square surveys and investigation items. So do reports they made or that are about them, and the moderation log. `tests/auth/test_account_deletion.py` says which of the two each user column is, and fails for a new one.

### Location sensitivity

See Decisions 0005 and 0032. A finding's `sensitivity` is `open` or `protected` (`vocab.Sensitivity`), and the database's check on the column allows those two. A finding that a database still holds at a level an earlier version stored and this one dropped is moved to `protected` by `create_schema`, before it makes that check again (`db._DROPPED_VALUES`), so the deploy that drops a level never meets one. Moderation log entries that name such a level keep it as written, and the log shows it as stored. `location_public` holds the position anyone may see: the exact point for an open finding, and the centre of its 1 km grid square otherwise. It's written whenever the finding is saved through the ORM, so a change of level or location never goes through a bulk `UPDATE`. A database trigger refuses an open finding whose public position differs from its location, and a change from open to protected that leaves the public position exact. It can't check the square itself, because the grid is in Python.

| Viewer | open | protected |
|--------|------|-----------|
| Signed out | exact | 1 km square |
| Any signed-in member | exact | exact |

A banned or deleted account counts as signed out. Downloads are stricter: only the finder and trusted people, experts, moderators and admins among them, download a protected finding's exact place (`sensitivity.downloads_exact`).

A generalised finding is returned with `obscured: true`, the square's reference, and no outline. An outline, an investigation's area and any other GeoJSON geometry a client sends has at most 2,000 positions and 200 parts (`geometry_too_complex`). They are counted after the request's JSON is parsed and before shapely sees them, and the 1 MB limit on a request body (`security.BODY_MAX_BYTES`) bounds what is parsed. A path isn't GeoJSON and has its own limit of 5,000 points (`PATH_MAX_POINTS`, in [the findings area doc](architecture/findings.md#limits)). A geometry's structure is checked before shapely sees it (`schemas/shapes.py`): every part non-empty, a line of two positions or more, a ring of four or more that closes, a position of two or three finite numbers. GEOS can crash the process on a polygon with an empty hole. The map's GeoJSON carries each finding's anchor, and its line or shape as `properties.shape` only for a viewer who sees it exactly. What each reader is sent of a shape is in [the findings area doc](architecture/findings.md#what-each-reader-is-sent). The default level comes from the feature class: round barrow, long barrow, ritual monument and settlement earthworks default to `protected`, everything else to `open`. The finder, a trusted user or a moderator can raise a level. Only a moderator can lower one, through `PUT /mod/findings/{public_id}/sensitivity` with a reason for the log, and the plain route answers a moderator's lower level with `lower_through_moderation`. A new finding starts at the higher of its class default and the level requested, and a request below the default is honoured only from a moderator (`starting_sensitivity`). Changing the feature class to one with a higher default raises the level to that default. It never lowers a level, and a change between classes with the same default leaves the level alone (`level_after_class_change`, applied when the finding is saved). Experts and admins count as trusted here, and admins as moderators.

One function in `services/sensitivity.py` decides what a viewer sees, and every route that returns a finding goes through it.

Free text can say where a finding is too: a grid reference, a pair of coordinates, an easting and northing, a three-word address, a plus code, a map link in the forms map sites write them, `mlat=`, `cp=lat~lon`, `!3d…!4d…` and percent-escaped degrees among them, or any link into a map site, short links included (`services/text_positions.py` says what counts). Text is read as a person sees it, full-width figures as plain ones and format characters skipped, and in time proportional to its length. Creating or editing a finding that isn't open refuses a title or description holding one with 422 `position_in_text`, naming each field in `details`, and so does a change of class that raises the level while the title or description holds one. Adding a mention or an evidence link whose address holds one to a finding that isn't open is refused the same way, naming `body.url`. For anyone who doesn't see a finding's exact position, `sensitivity.visible_text` replaces every such position with `[position hidden]` in everything served about it: its title and description, answer notes, comments, evidence titles and notes, mention titles and notes, the title and note of an investigation item that holds it, and the same fields in downloads, which follow the download rule. Text written while the finding was open and later raised is hidden the same way, as is text other people wrote. A web address someone attached to a finding, an evidence link or a mention's `url` and `canonical_url`, goes only to people who see the exact position (`sensitivity.visible_url`): anyone else gets a video's or a DOI's address rebuilt from its identifier alone, or null, and a mention's thumbnail only beside a video's address (Decision 0021). Moderators see every position exactly, so their views of reported content carry addresses as stored.

What is written and drawn in an investigation goes through a `sensitivity.PositionGuard` for the reader (`investigations.position_guards`, Decisions 0021 and 0023). It holds the findings the reader doesn't see exactly, or for a download doesn't download exactly, that the investigation holds or has ever held (`investigation_held_findings`), hidden and withdrawn ones included. It also holds every such finding within 1.5 km (`NEAR_HIDDEN_M`) of something drawn in it, whichever investigation holds that finding or none, withdrawn ones included (`sensitivity.hidden_near`). A finding a moderator has hidden takes no part in that 1.5 km rule: `hidden_near`, and `near_hidden_clause` for the `bbox` match, leave out any finding with `hidden_at` set. While it holds one, the investigation's title, wherever it is shown, the activity feed included, its summary and notes and every item's title and note lose the positions written in them, and a reference's link is given only when it is a DOI's or a video's address rebuilt from its identifier. A saved view whose centre or a height profile whose line comes within 1.5 km of such a finding is returned with `unavailable: near_protected` and without its view or profile, and an area within 1.5 km is returned, and matched by `bbox` in `GET /investigations`, as `area_squares`: the whole 1 km squares of the grid under it that its bounding box covers (`sensitivity.square_cover`), so it never cuts a finding's public square. Everyone signed in sees every finding exactly on the page, so there the guard holds findings only for a signed-out reader, who can't edit. Apart from the guard, the title and note of a finding item lose the positions written in them for a reader who isn't shown its finding, because a moderator hid it, its finder withdrew it or it is gone. That reader may be an editor, so `PATCH .../items/{id}` refuses a change to either with 409 `item_unavailable`, and the interface offers no edit for such an item. In a download it holds the protected findings of anyone but their finder and trusted people, the reader's own items included. The downloads say the same of a view or profile held back, with no geometry. This is worked out when the investigation is read, so items saved earlier are covered. A title search matches `title_public` for them, so it can't read a hidden position out a figure at a time. Queries on behalf of signed-out visitors filter and sort on `location_public` only. Downloads use the generalised position for protected findings unless the person downloading is the finder or trusted (`sensitivity.downloads_exact`, beside the other viewer rules). Suggested records and the search box start from the position the viewer may see, so for someone who sees only the square, distances, order and the set returned are the same wherever in the square the finding lies. `tests/test_routes.py` lists every route the app serves and names the test, in `tests/findings/test_leaks.py` or beside the route's own tests, that tries each one carrying a position as every viewer against every level, and fails when a route has no row.

Findings reach the map through `GET /findings?bbox=&format=geojson`, not through cacheable tiles, because the answer depends on the viewer. The `bbox` matches the position the viewer is allowed to see, so an obscured finding matches by the centre of its square, and for a viewer who sees a finding exactly it matches the finding's shape as well. The frontend widens the box it asks for by 500 m on each side so that a square covering the view is returned even when its centre is off screen. The map asks at every zoom. When the answer carries `next_cursor`, the map draws what came and says on the map that not every finding in view is drawn, and zooming in shows the rest.

### Second looks

Decision 0008 makes second looks blind. These rules keep each answer independent after it's given:

- An answer is final. Answering reveals the finding and everyone's answers, so `PUT /findings/{public_id}/observation` refuses a different answer with `answer_final`, and only the note can change. `DELETE` marks the answer withdrawn, which stops it counting. The same answer given again restores it, and a different one is refused.
- An answer can come in two steps, so the detail is asked for after it (`docs/UI.md`). `PUT .../observation` with `detail_follows: true` carries `visible` alone. The answer is stored and counts at once, and the reply is `{revealed: false, observation}`. `POST .../observation/reveal` then adds the class, period, explanation, checks and note, or nothing, once, and its reply is the reveal (`revealed: true`). The detail counts exactly as detail sent with the answer. Asked again, it gives the same reveal while the detail matches and `answer_final` otherwise. A `PUT` of the whole answer on one still waiting adds its detail the same way. `observations.revealed_at` records the reveal. Until it is set the reviewer is someone who hasn't seen the answers on every route, and a finding's page gives them `my_observation` with `revealed: false`, so they can finish from there. A request that carries the answer and its detail without `detail_follows` reveals at once, as before. The reveal's `tier_before` and `state_before` are the finding's before the first step, kept on the observation (`tier_at_answer`, `state_at_answer`), so it shows the move the answer made. A reveal that carries any detail or a note is refused where the `PUT` would be (`finding_withdrawn`, `own_finding`, `location_hidden`). One that carries nothing is allowed on a finding withdrawn since the answer, so the answers the reviewer is owed are never stranded.
- Answers, evidence and votes come only from someone who sees the finding's exact position. Anyone else gets `location_hidden`. Every signed-in member sees it, and the routes refuse a banned account before this check, so it holds in the services (`findings.require_exact`) for any caller that skips them. Comments stay open to every contributor.
- `observation_added`, and a tier or state change that an answer or its withdrawal causes, are recorded with no actor, so followers can't tell how anyone answered.
- A viewer who may not see the answers gets the next steps that second looks meet without `people`, `weight_needed` or a number in the prompt.
- "May see answers" means being the finder or having an answer that has been revealed, even if it was taken back later (`findings.answers_visible`).
- A finding page names the people who answered only to those who may see answers (Decision 0010). Everyone else gets no credit for an answer, neither a name nor a count.
- Suggested records weigh a record's fit with the community class only for those who may see answers, so neither `type_fit` nor the order gives the class away.
- A profile counts and lists the findings a person took a second look at only to that person. Everyone else gets `counts.second_looks` as null and an empty `kind=second_look` list, because someone polling a profile would see when an answer arrived, and the unnamed tier change at that moment would show which way it went (the reasoning of Decision 0010).

A change of someone's role, a ban and its lifting reassess only the findings their present role still bears on, their own and those with their evidence or verifications, and never move a score through their answers or votes (Decision 0019). So a moderator who changes a member's role and changes it back, or bans them, learns nothing about how they answered, and nobody watching sees a burst of events on the findings they answered.

Known limits, accepted for now. A finder's feature class is weighed by the finder's role today, so changing a finder's role can move class agreement on their findings: that says how unnamed people classed the feature, in aggregate, never who said what. A review card carries the finding's `public_id`, because the answer is sent to it, so a reviewer who opens the finding's page first sees the claim there, as Decision 0008 allows. The tier, the score (`confidence` and `assessment.score`) and the order of the review queue (`answers_to_next`) all follow from other people's answers and reach people who haven't answered. None carries a name, but someone who watches a page can tell that an unnamed answer moved the score up or down (Decision 0010). The feed, notifications and the event stream announce each `observation_added` as it happens, with no actor, so they too say that someone answered and when, not who. An answer given in two steps counts at the first, so before choosing the detail the reviewer can see the tier, score and next steps move with their own answer, as any visitor can. The detail they then give isn't quite as blind as detail sent with the answer. The review queue and the help-wanted lists page by an offset held in the cursor, because their order changes as people answer, so a card can move between pages or appear twice.

### Moderation

Any contributor can report a finding, comment, piece of evidence, mention, photo, person or investigation, with a reason from `vocab.REPORT_REASONS` (served in `/meta` as `report_reasons`) and a note only moderators read. A report names its target as the API does: a finding or an investigation by public id, a person by handle, anything else by id. Something the reporter can't see is `target_not_found`, a second open report on the same target is `already_reported`, and a report on a target within 24 hours of the same person's report on it being dismissed is `recently_dismissed`. Moderators see the queue oldest first, without the reports they made or that are about them or their work. A report for an intimate image or an untrue statement about a person carries `due_at`, 48 hours after it was made, because the law gives that long. Resolving a report, upheld or dismissed, resolves every open report on its target. Nobody resolves a report they made or one about them or their work. A reporter is told nothing more, and nothing a moderator writes reaches any one member (Decision 0009).

Everything under `/mod`, the queues, the eligible list and the log included, needs the welcome step finished (`onboarding_required`), because that step is where a person accepts the terms. `tests/test_routes.py` marks such a read with `welcome`. A moderator hides and unhides findings, comments, evidence, mentions, photos and investigations, except their own (`own_content`), and removes someone else's comment, evidence or mention only by hiding it: `DELETE /comments/{id}`, `DELETE /evidence/{id}` and `DELETE /mentions/{id}` are for its author alone (`mention_forbidden`). A moderator raising the level of someone else's finding through `PUT /findings/{public_id}/sensitivity` is logged as `change_sensitivity` with no reason. It takes effect on the next request. A hidden finding is seen only by its finder and moderators. A hidden comment reads as removed, with no author and no body, to everyone but its author and moderators, and leaves `comment_count`. Hidden evidence stops counting at once, the finding is reassessed, and it leaves finding pages, credits and exports for everyone. A hidden mention leaves `mention_count` for everyone, and the finding's list, the recent feed, profiles, the feed and notifications for everyone but its adder and moderators, who see it marked `hidden`. While it stays hidden it holds its address on the finding, even once its adder removes it, so neither a member nor the channel scan can add it again (`mention_hidden`, 409). A hidden photo is served only to its uploader and moderators. Every read route says in `tests/test_routes.py` how it leaves hidden things out, naming the walk in `tests/moderation/test_hidden_everywhere.py` that reads it as every kind of viewer after each kind of thing is hidden, or why it holds nothing a moderator can hide.

A moderator makes a member trusted, from fifty points (`not_eligible` below that), puts a trusted member back, and marks or unmarks an archaeologist as expert. Only an admin makes or unmakes a moderator, admins are made outside the API, and nobody changes their own role. `GET /mod/users/{handle}` shows one person to a moderator, a banned or deleted account included, with no email address or sign-in identity, and `actions` in a finding page's shape (`{allowed, reason}`) for `ban`, `unban` and each role under `roles`, worked out by running the routes' own checks (`services.actions.person_actions`): the reason is the code the route would answer, or `current_role`. `GET /mod/users/eligible` lists members with fifty points who aren't trusted, with the findings their points came from, the other people on each, and those people counted across all of them. Second looks stay blind (Decision 0008): the people who answered a finding, and points earned by answering it, are tied to it only for a moderator who found or answered it. Otherwise answer points are added up in one source with no finding and the reason `second_looks`. A ban ends every session the person has, and while it lasts their evidence and verifications stop counting, their evidence leaves pages and exports, and evidence they verified no longer names them. Their second looks and votes keep counting as they were given, because a score or a count that moved the moment a named person was banned would say how they had answered or voted (Decision 0019). Their square surveys stop counting in coverage and in choosing the next square. Every finding they marked, added evidence to or verified is reassessed with no actor, and again when the ban is lifted. The ban's answer gives the person and the sessions ended, nothing about their findings. Their findings, comments, mentions and investigations stay, and their profile answers `user_not_found`. Their events and notifications leave every list, because the feed drops a banned actor's rows. An event stream they hold open carries only what the public feed lists until it ends. An invitation waiting for them can't be accepted while they are signed out, and stays. A moderator bans anyone below moderator, and only an admin bans a moderator. Every one of these actions, and every photo approved or refused, writes a `moderation_actions` row, which `GET /mod/actions` lists newest first.

### Photos

`POST /media` takes the image as the request body, at most 15 MB, refused unread when `Content-Length` says more. Pillow must read it as a JPEG, PNG or WebP still image of at most 50 million pixels, fully decoded, and a picture over 4096 by 4096 pixels needs at least one byte of file for every 200 pixels (`image_too_many_pixels`). A multi-picture JPEG is read as its first picture. A JPEG is decoded at a half, a quarter or an eighth of its size where that leaves at least 3072 pixels across, and one upload is decoded at a time in the process: one that waits more than 30 seconds is `uploads_busy` (503). The pixels are copied into a new image, turned the way the EXIF orientation says, scaled to at most 4096 pixels across and saved as a JPEG, or a PNG when it has transparency, so no EXIF, GPS, XMP, ICC profile or text survives. The file is stored under a random 128-bit key that no response contains. An upload matching a refused or hidden photo byte for byte is `media_blocked`. `GET /media/{id}` serves the photo as `image/jpeg` or `image/png` with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and an inline disposition. It is always sent `private, no-cache`, varying by cookie, approved or not. Before approval it goes only to its uploader, moderators, trusted members and archaeologists. After it, a photo attached to a finding goes only to people who see that finding's exact position, and never when the evidence or finding is hidden or the uploader banned. Anything refused is the same 404, `media_not_found`, as an id never used. Refusing a photo deletes its file once the refusal has committed, as account deletion does, so a failed commit leaves the photo with its file. An approved photo is hidden, not refused.

## Events

`services/activity.py` has `record(db, kind, actor, finding=None, investigation=None, data=None)`. It inserts an `activity` row, creates notifications for the finding's followers, and after commit sends a small payload through PostgreSQL `NOTIFY fieldclub_events`. One listener per process fans payloads out to connected event-stream clients. Because the bus is PostgreSQL, it works across instances. It needs a connection of its own, which a transaction pooler can't give. So `config.database_address` turns Fly's pooled address, `pgbouncer.<cluster>.flympg.net`, into its direct one, `direct.<cluster>.flympg.net`, and gives every address the psycopg driver. It finds the host by SQLAlchemy's own rules, so a password holding a raw `/` or an address with options and no database name is rewritten too. That applies to `FIELDCLUB_DATABASE_URL` and, on a Fly machine only, to `DATABASE_URL`, which is read when the first is unset and is what Fly attaches to an app. Off Fly, a `DATABASE_URL` in the shell is ignored. `fieldclub-api` logs the address it will use at start-up, and every process logs it at its first connection, both with the password masked. Every connection asks for TCP keepalives and a 30 s user timeout, set in `db.KEEPALIVES`, so a connection the database dropped while Fly had the machine suspended is found. The ingest runner's source lock lives on a connection of its own too, and a full run checks that connection still answers before it deletes anything, failing with `ingest_lock_lost` when it doesn't.

An event caused by a second look has no actor (see Second looks above). A `tier_changed` event caused by adding, removing or verifying an evidence item names it as `details.evidence_id`, so the follow-up timeline can tell which item moved a finding. One caused by a vote names no item, because with the voter as actor it would say how they voted on it, and an item gives its votes only as counts. One caused by a second look names no item, and carries nothing but the move.

Nobody is notified of their own action. A second look's events have no actor, so `record` takes the answerer as `quiet_for` and leaves them out of the notifications instead. `activity.location` is the centre of the finding's 1 km square for every finding, and `activity.relocate` moves it when the finding moves.

`GET /activity` and `GET /notifications` list an event only while what it is about can still be seen: not on a finding that is hidden from the viewer or withdrawn, not on an investigation that isn't public or is hidden from the viewer, not by a banned account, and not about a comment, evidence or mention (`data.comment_id`, `evidence_id`, `mention_id`) that has been deleted or is hidden from the viewer. An invitation's notification is listed while the person is still invited or a member. A deleted actor is shown as no one. Both are newest first by id. The feed's `bbox` matches `activity.location`, so a shrinking box can find no more than the square, which everyone may see, and each item's finding carries its position as the viewer may see it.

The event stream is the one `async` endpoint, served on the event loop (`services/events.py`). Each process runs one hub: a psycopg `AsyncConnection` holds the `LISTEN`, and each client is an async generator waiting on its own bounded queue, so a client costs a coroutine and holds no worker thread and no database connection. Before announcing an event the hub checks, once per event and in a worker thread, that a signed-out visitor's feed lists it, and reads its square for clients filtering by box. The square never leaves the server: a client receives `{id, kind, finding, investigation, actor}` and refetches through the API. A client that falls `FIELDCLUB_EVENTS_QUEUE_SIZE` events behind is dropped with a `dropped` event, and keeps its place under the caps until its response ends, because a client that stopped reading may still hold the connection. The listener reconnects after any failure and sends `resync`, because events sent meanwhile are lost. It runs `SELECT 1` every 15 s, whatever arrives, and at once when a client subscribes, and gives the connection up when no answer comes within 10 s. Making the connection and its `LISTEN` have the same 10 s limit, so a reconnect can't hang on a peer that accepts it and never answers, and a connection that went silent while the machine was suspended is replaced within seconds of the first visitor after the resume. An event the hub can't check is skipped, never announced unchecked. Streams send a `: ping` comment every `FIELDCLUB_EVENTS_HEARTBEAT_S` and end after `FIELDCLUB_EVENTS_MAX_STREAM_S`. One address may hold `FIELDCLUB_EVENTS_MAX_PER_ADDRESS` streams, 8 unless set and never more than a quarter of `FIELDCLUB_EVENTS_MAX_STREAMS`, so a few addresses can't take a process's every stream, and a process `FIELDCLUB_EVENTS_MAX_STREAMS`, beyond which the answer is 429 `too_many_streams`. A browser's `EventSource` doesn't retry after a 429, so the frontend reopens the stream after a delay, or polls, when it finds the stream closed. `fieldclub-api` ends every stream with `closed` before uvicorn waits for open responses, so shutdown doesn't wait for them.

A person sees their own second looks on their profile as `second_look`, without a date and in the findings' order (see Second looks for why nobody else does). The reputation others see leaves out the points answers earned (`observation_corroborated`, `observation_ruled_out`), and the itemised points are the person's alone. Profiles of deleted and banned accounts answer `user_not_found`. A handle-only account (16 to 17, or no band yet) shows no bio either.

Activity kinds: `finding_created`, `tier_changed`, `state_changed`, `observation_added`, `evidence_added`, `comment_added`, `mention_added`, `followup_logged`, `investigation_published`. `investigation_invitation` is a notification only, written by `activity.notify_invitation`, never an `activity` row.

The payload carries ids only, and `activity.location` is the centre of the finding's 1 km square, never an exact position.

## Mentions

`services/unfurl.py` reduces every address to one canonical form: each way of writing a YouTube link becomes `https://www.youtube.com/watch?v=<id>` with the start time in `start_seconds`, Vimeo links become `https://vimeo.com/<id>`, a DOI in any form becomes its lower-case doi.org address without query, fragment or trailing slash, and anything else loses its fragment and tracking parameters, has its query sorted and its unreserved characters unescaped. A finding's mentions are compared by `match_key`, the canonical address less `http` or `https`, a leading `www.` and a trailing slash. An address holding a format character (a bidi override, a zero-width character) is refused, and page text loses them. It fetches the title, author, thumbnail and date without keys: oEmbed for YouTube and Vimeo, doi.org content negotiation for CSL JSON, and Open Graph tags or `<title>` for a page. Results are cached in the process for an hour, failures for five minutes. A fetch that fails or is refused leaves the mention with its address alone. Thumbnails are kept only on https and only from YouTube's and Vimeo's image hosts: a page's own image is never kept, because the member chose its site and it would learn who looked at the finding. Fetches the cache can't answer spend one budget for the process (600 an hour); when it is used up the address is left unfetched and that isn't cached. A page is read in the charset its server names only when that is one of the charsets web pages are written in (`safe_fetch.TEXT_CHARSETS`), and as UTF-8 otherwise, and anything that breaks the reader counts as a failed fetch, never an error.

Every such fetch goes through `safe_fetch.fetch`: http and https only, ports 80 and 443, no credentials, the host resolved once and refused if any address is private, loopback, link-local, shared, reserved, multicast or a cloud metadata address (IPv4 in odd notations or inside IPv6 included), the connection made to the checked address with the name as `Host` and TLS server name, redirects followed by hand with the same checks (three by default), the content type checked, the body capped after decompression, and a deadline on the whole fetch that bounds every socket operation, headers included. The name lookup is given up on after five seconds. These fetches use a client of their own with eight connections, so they never take the shared client's. `POST /mentions/preview` and `POST /findings/{id}/mentions` are rate-limited per contributor after the contributor check, and end the request's transaction before fetching, so no database connection waits on a stranger's server.

Adding a mention bumps `mention_count` and records `mention_added`, which tells the finding's followers (the finder and everyone who helped) except whoever added it. A mention never touches the confidence engine. `GET /mentions/recent` lists mentions on findings the viewer may list, newest first, each with its finding's position from `location_out`. Withdrawn findings and removed mentions are left out, and hidden ones for everyone but their adder and moderators. Only the person who added a mention removes it, and that blocks nothing, so anyone may add that address again. A moderator hides one instead, the scan's included, through `/mod/mentions/{id}/hide` (see Moderation).

`fieldclub-jobs purge-sign-ins` deletes expired sessions and old sign-in links (see Accounts), and every `fieldclub-jobs due` run does the same first. `fieldclub-jobs scan-channels` reads each enabled channel's public feed, one at a time with a pause between them and conditional requests, and adds an `auto_detected` mention with no member for every link in a video description to `<FIELDCLUB_PUBLIC_URL>/f/<public id>`. `fieldclub-jobs refresh-sources` runs each enabled bulk source's connector, and each reference loader, one at a time, when its last completed full run is older than its `max_age` (a week when it declares none). A source that lacks a setting it needs, such as the contact address Wikidata asks for, is skipped, and one that fails stops there until the next refresh. It never allows a shrink, so a full run that would remove more than `FIELDCLUB_INGEST_MAX_SHRINK` of a source fails and is counted as failed. Both exit non-zero when anything failed, after carrying on with the rest. `fieldclub-jobs due` is for a scheduler that starts it every hour, as Fly's does (`jobs/due.py`). It runs the scan when some channel is watched and none has been checked for five hours, which with the hour Fly takes to start it keeps scans about six hours apart, and the refresh when the hour is 03 UTC, the scan first. It exits non-zero when any of them failed.

## Terrain service

The shape is fixed. The sources are filled in from the catalogue in `docs/sources/`, `lidar.md` and `lidar-england-bulk-supply.md` among them.

`terrain/sources.py` defines `ElevationSource.read(bounds_3857, width, height) -> float32 array` with NaN for no data, and `cacheable_for(...)`, whether that read can change under its edition. `terrain/render.py` asks the source for a tile's bounds plus a buffer, so neighbourhood filters have real data at tile edges, then crops. The buffered elevation array is cached once per tile, so switching style doesn't hit the upstream again. Rendered tiles are cached too. Both caches use `Storage`, which is local disk in development and a bucket in production. Each kind of data is a namespace (`tiles`, `media`) under `FIELDCLUB_S3_BUCKET`, unless `FIELDCLUB_S3_NAMESPACE_BUCKETS` gives it a bucket of its own, as production does for uploaded photos. A bucket is reached through the S3 interface, with the `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_ENDPOINT_URL_S3` that Fly sets when a Tigris bucket is attached. `AWS_REGION` is `auto` when unset. The settings refuse to load without the first three whenever storage or a terrain folder is in a bucket.

`terrain/visualise.py` holds the pure numpy functions: hillshade, multi-directional hillshade, slope, local relief, sky-view factor, openness, and the blends. Each takes elevation and ground resolution in metres and returns an array with a fixed stretch, so adjacent tiles always match. Kernel sizes are given in metres and converted to pixels per zoom.

Elevation is read only from the mirror (`terrain/mirror.py`): one COG per 5 km tile, LERC_ZSTD at 1 cm, 512-pixel blocks, overviews at 2, 4 and 8 m, in a local folder or under `s3://`, which GDAL reads through `/vsis3/`. GDAL reads the credentials from the environment itself, and `terrain.blobs.configure_gdal_for_s3` gives it the endpoint's host, HTTPS as the address says and path-style requests, none of them a secret. It puts them in the process's environment as each program starts, because an option set through rasterio reaches only the thread that set it, and tiles are drawn on threads of their own. A tile that isn't mirrored is converted from Defra's source file on disk if it is there, or fetched from the SFTP bulk supply (`terrain/sftp.py`), once however many requests want it. Nothing the API serves waits for that (Decision 0016): a map tile or a profile that needs such a tile starts adding it on a pool of `FIELDCLUB_TERRAIN_FETCH_CONCURRENCY` threads of its own (`terrain/prefetch.py`), each tile once, and answers `elevation_preparing`; a tile whose background attempt failed answers that failure for a minute, with the code and status the foreground would give (502 `elevation_fetch_failed` for one tile, 503 `elevation_supply_refused` when the supply refuses our login or shows the wrong host key, 503 `elevation_unavailable` otherwise) and a `Retry-After` for when it is tried again, and the mirror's own memory of failed tiles below holds longer. With `FIELDCLUB_TERRAIN_API_FETCH` off, as on the web app on Fly, which holds no supply login and a key that only reads the mirror, the API adds nothing: such a tile is answered 503 `elevation_unavailable` for a minute at a time, logged as a warning, before any lock is written. Such a server lists the mirror when it starts and logs an error whenever the tiles it lacks change, and a deploy first runs `fieldclub-terrain check`, which fails when a catalogue tile is missing or when one can't be read through GDAL on a thread of its own (`release.py`, Decision 0027). A point height never fetches. Where the 1 m tile exists but isn't mirrored it gives the overview's height if it has one, and says `preparing` while the tile is being added, `failed` while its failure is remembered, and `not_mirrored` otherwise. On shutdown the lifespan cancels queued fetches and tile draws (`terrain.service.close_terrain`); a fetch already running isn't waited for, and the next request for its tile starts it again. The commands fetch in the foreground. In a bucket that holds across servers too, through a lock object per tile that is created only if absent, rewritten by its holder while it works, and taken over once it hasn't been rewritten for `FIELDCLUB_TERRAIN_LOCK_STALE_S` (`terrain/blobs.py`). The create sends `If-None-Match: *`. A rewrite and a take-over send `If-Match` with the ETag of the lock they saw, and a refusal answers 412, or 409 while another conditional write to the object is under way. A refused rewrite is tried again while the lock still names its holder, so only another owner, or none, ends a heartbeat. A 412 or a 409 is a refusal, and a 404 means no object only with the code `NoSuchKey`: a missing bucket (`NoSuchBucket`) or a refused key is an error, not an empty folder. An ETag comes from an object's bytes, so every write of a lock carries a random value of its own, and a take-over can only remove the very lock that was seen stale. A mirror tile is uploaded in one request made only if nothing has its name, and its stored size is checked afterwards. A tile whose every copy was unreadable isn't fetched again for six hours, recorded under `failed/` in the mirror. A read that hears nothing for 60 s gives up, and a failed attempt waits before the next, twice as long each time. A refused login or a wrong host key isn't retried: fetches pause for 15 minutes, and a `fieldclub-terrain mirror` run stops, as it does after five failed tiles in a row. The mirror only adds files and never replaces one. The national build prunes only its own `england-<build>.tif` files, and the settings refuse a mirror and overview folder that are the same or one inside the other; on Fly nothing else enforces this, because one key writes both (infra/README.md). `terrain/catalogue.py` lists the 5,877 tiles, so a tile that doesn't exist costs no network call. From zoom 13 up, map tiles read the 1 m mirror and start fetching what is missing. Below 13 they read the national overview (`terrain/national.py`, `terrain/overview.py`, Decision 0012): one COG at 8 m built from the mirror's own 8 m copies, named in `national.json` and rebuilt with `fieldclub-terrain national build`. A low-zoom tile is cacheable when the build holds every 5 km tile it touches, and otherwise draws the mirror's tiles uncached. Beyond the reach of its data a Terrarium tile takes the overview's height, then sea level, which is wrong over the 351 km² North York Moors gap in the 2022 composite: the DEM draws a pit there until the post-2022 tiles fill it. The coverage layer's capture years come from Defra's survey index, packaged as `terrain/data/england-dtm-2022-years.tsv` by `fieldclub-terrain years build`. The LIDAR sources have `sources` rows (`terrain/attribution.py`), which `fieldclub-terrain sources` and every command that stores elevation write. `fieldclub-terrain` mirrors tiles, builds the overview, warms the tile cache and reports on all three. The terrain folders default to places under `FIELDCLUB_VAR_DIR`, which storage and ingest use too. A relative `FIELDCLUB_VAR_DIR` is resolved against the repository root, so all three find the same folder from any working directory. The styles, their parameters and versions are in `terrain/styles.py`. Terrain tile URLs carry `?v=`, a token of the style version, the elevation format and the data editions, the overview's build among them: a tile asked for with the token of the build it was drawn from is sent as immutable, one from a source that is still filling as `no-cache`, and `tests/terrain/test_versions.py` fails when pixels change without a version.

## Ingest

A connector subclasses `ingest.base.Connector`, declares its `Source` row, and implements `fetch() -> Iterator[RecordIn]`. The runner upserts the `sources` row first, batches upserts on `(source_key, external_id)`, removes rows that vanished upstream when a full run completes, writes an `ingest_runs` row and rebuilds the source's `record_cell_counts`. A full run has no `bbox` and no `limit`. Every record's name, summary, type and monument types have their HTML character references decoded as they are stored (`runner.plain_text`), however many times over a source escaped them. A record's address is kept only when it is an absolute http or https address of at most 2,000 characters with no credentials (`schemas.common.web_url`), and its name and summary are cut to 500 and 20,000 characters. The `rest` reader follows a next-page address only on the scheme, host and port of the first page, and a redirect only to the same host, at most five times, checking each hop itself rather than letting the shared client follow it. A run that yields nothing fails, and so does a full run that would remove more than `FIELDCLUB_INGEST_MAX_SHRINK` of what is stored, unless it is run with `--allow-shrink`. `uv run fieldclub-ingest list|run <key> [--bbox] [--limit] [--allow-shrink]` drives it. Runs are idempotent. Connectors hold no credentials. A source that needs a key reads it from settings and is skipped when the key is absent. Shared readers in `ingest/adapters/` do the fetching: ArcGIS, WFS, SPARQL, files and downloads, and `rest` for paged JSON, which checks the distinct items it reads against the count the service reports and can keep each page for a day. `ingest.base.in_britain_and_ireland` is the coarse test that leaves out the Continent, which the runner's own box for the isles still holds. A source that only cross-walks identifiers, such as Wikidata, declares `enabled=False`, so its records stay out of the map, tiles and search (Decision 0011). `ingest/connectors/README.md` is the guide to writing a connector.

The National Heritage List layers share `ingest/connectors/he_nhle_hub.py`: the Open Data Hub export address, the licence, the currency statement and the list-entry link. Where a layer comes as points and as polygons of the same entries, only one is enabled, so no designation is found twice. The listed buildings keep their points, which cover every entry, and the notices and certificates keep their polygons. The other layer of each pair is registered disabled: its records are stored when it is run and hidden from search, lists and tiles.

A record is a thing, not a feature. Where a source publishes several features for one thing, its connector joins them: York's HER gives a point, lines and outlines under one `MonUID`, and `york-her-monuments` stores one record per `MonUID` with every part as one geometry, which is why it holds about 5,200 records for 9,662 features. The undesignated parklands do the same: parts of one name and HER within 2 km of each other are one record, a MultiPolygon, and parts further apart, or marked distinct in a comment, stay separate parks. A York monument that is a point plus an outline is a GeometryCollection in the record API, but its vector-tile geometry keeps only the highest-dimension parts, so tiles show its outline and not its point. When a source has no identifier of its own, the connector hashes the fields that name the thing and raises if two features give the same hash. A source whose own coordinates are wrong is placed from the better field: the lost villages are placed from their grid references, and the layer's geometry is used only when the reference does not parse. `ArcGISLayer` pages by offset where it can. A layer that is a view of several shapes needs `by_object_id=True`, because its offsets count rows the layer hides.

Some sources are not records. Natural England's CRoW access land (42,054 polygons), the National Historic Landscape Characterisation 250 m grid (2.1 million cells) and the Forestry Commission's woodland opportunity map (552,503 cells) say where one may walk or what kind of landscape lies under a cell. They hold no sites to find. They belong in the map layer catalogue, not in `records`, where they would fill search, nearby results and suggestions with polygons that are not sites. They have no connector.

A reference loader in `ingest/reference/` fills `places` or `admin_areas` instead of `records`. It declares its `Source` row like a connector, and each run replaces its rows in one transaction and writes an `ingest_runs` row. `fieldclub-ingest run <key>` runs loaders too: `--bbox` replaces only the rows in the box, and `--limit` is refused, because a run that kept N rows would delete the rest. `os-open-names` fills `places` with Great Britain's populated places, landforms, water, woods and the airports, harbours and stations people navigate by, about 270,000 names, and leaves out postcodes, roads and buildings. A place's `rank` is its kind in the hundreds (a city 9, a town 8, a village 7, down to a wood 2) plus up to 99 for the size of its bounding box. The search box orders names that start with the query by rank, and the rest by similarity first, under the same time limit as record search. It then ranks places and records together (`services/name_rank.py`): first the names that fit, a name that is the query or whose first part before a comma or colon is, then names that start with it as whole words, then part-way through a word, then names that hold it; within each, places and designations of national importance (scheduled monuments, World Heritage Sites, registered parks, gardens and battlefields, protected wrecks) before other records. Listed buildings, reports and radiocarbon dates that fit come after all of those, and loose matches last, by similarity. A name one source repeats is shown once. Record search reads its candidates in the same order. Each place carries its source, so its attribution goes with it. `ons-countries-2025` and `ons-counties-2025` fill `admin_areas` with the four nations and ONS's counties and unitary authorities, simplified to 20 m as one coverage so neighbours share their borders, and each reaching 2 km out to sea from a coarse copy of its coast, except where it is that close to another area. A point at sea in no nation takes the nearest nation within 10 km for a new finding, and the viewers of every nation that near for context links. A finding's page gives a viewer who sees only its 1 km square the square's nation, which is none when the square meets two (`sensitivity.visible_nation`).

Eight more Historic England layers are connectors beside the scheduled monuments one, read from ArcGIS FeatureServers, except the detailed mapping, which is the Hub's 4.7 GB GeoPackage export because its FeatureServer pages time out near object id 400,000: the three Aerial Investigation and Mapping layers (detailed mapping, monument extents, project areas), Heritage at Risk 2026, Research Spatial Reports, Turning the Plough 2, the removed designations and the Greater London priority areas. They take the Hub's address, its export address and the Open Government Licence address from `he_nhle_hub.py`. A layer with no identifier of its own gets a key from `FeatureKeys` (`adapters/common.py`): a hash of the fields that name the feature and its geometry in the source's own British National Grid coordinates, to a tenth of a metre, so a change of PROJ or datum grid doesn't renumber it. The detailed mapping skips an exact repeat and tells two interpretations of one outline apart by a hash of their attributes. The project areas are survey coverage rather than finds, so `nearby()` and the record suggestions leave out records of a type in `vocab.COVERAGE_RECORD_TYPES`. HER boundaries is not a connector, because the records table has no category for it.

## Frontend

A single-page app. The map is always mounted. Panels and modes are routes layered over it: `/` explore, `/?panel=none` the bare map with no panel open, `/mark` marking a finding and `/mark/:draftId` a finding draft, `/f/:id` a finding, `/r/:id` a record, `/review` second looks, `/help` help wanted and `/help/:kind` one kind of it, `/mentions` the recent mentions across the map, `/activity` the activity feed, `/scan` scan a square, `/i/:id` an investigation, `/u/:handle` a profile, `/mod` moderation, `/account` the signed-in person's own details, `/signin/email` where an emailed link lands, `/about` with its notices at `/about/:notice`, and `/guide`. The API client and its types are generated from the backend's OpenAPI schema with `pnpm gen:api`, so the two sides can't drift. Vocabularies, tier definitions and the layer catalogue come from `/meta` at start-up. The frontend hard-codes none of them.

Every link drawn from data goes through `safeHref` in `map/attribution.tsx`, which keeps only absolute http and https addresses, or `safeLinkHref`, which also keeps a path on this site, and anything else is shown as words. `src/test/linkSinks.test.ts` reads the source and fails on an `href` taken straight from a field such as `.url` or `.homepage`. People are shown by their name and initials (`ui/Avatar.tsx`), never a picture (Decision 0020). Nothing the interface loads comes from a host the backend's `Content-Security-Policy` doesn't name, and `pnpm e2e:full` fails on any violation. The production build writes no source maps.

<!-- Accounts and drafts (f0/account). -->
`features/account/session.ts` is the only place that knows who is signed in. `useSession()` answers from `GET /auth/me` with `status` (loading, signed-out, signed-in, or unknown when the server couldn't be asked), `me`, `role`, `needsWelcome`, and `ready` for someone signed in and through the welcome step. A 401 from any request signs the whole interface out, and a 403 `onboarding_required` from any request asks for the session again and opens the welcome sheet (`onUnauthorised` and `onForbidden` in `api/client.ts`). Whenever the person changes, every query whose answer depends on the viewer is dropped and asked again, and every listener given to `onPersonChanged` is told, so a feature can forget what it keeps outside the cache. The finding last chosen, and what drafts saved for the last person (a finding, or what an answer revealed), are forgotten this way. A sign-in or sign-out in another tab is picked up through a `localStorage` signal that holds no personal data.

A feature gates a save with `useRequireAccount()` from `features/account/requireAccount.ts`. The function it returns resolves at once with the person when they are ready. Otherwise it opens the sign-in sheet, or the welcome sheet, over the current view, and resolves when they are ready or rejects with `AccountRequiredError` if they close it. When the session isn't known and the server can't be asked, it says so and rejects with `SessionUnknownError`, a kind of `AccountRequiredError`, rather than treating the person as signed out. A provider sign-in is a full-page round trip, so work that has to survive it is a draft. The sign-in sheet's provider buttons are links to `/auth/oauth/{provider}/start?next=`, with `next` set to the current path and map position. `features/account/next.ts` checks every `next` by the rules in "Accounts", and the app follows one only through the router. The emailed link's token is taken out of the address before the app renders (`features/account/emailLink.ts`), held in memory only, and sent nowhere but `POST /auth/email/verify`. A link opened in a browser that didn't ask for it asks the person to type the address they asked for it with, empty and never filled in, and shows no masked address. A different address is `email_mismatch`, and the page says that someone else's link would sign them in to that person's account and offers to ask for their own. A `signin_error` in the address opens the sign-in sheet with a message for its code and is then removed.

`features/drafts/store.ts` keeps signed-out work in `localStorage` under `fieldclub.drafts` as `{version: 3, drafts: [...]}`. A draft is `{id, kind, data, owner, createdAt, updatedAt, state}`, with `held` on a draft taken over at sign-in that waits for its maker to send it, where `kind` is one of `DRAFT_KINDS` (finding, observation, square) and `data` is the owning feature's JSON, at most `MAX_DRAFT_CHARS` long. A feature defines its kind once with `defineDraftKind<T>({kind, label, parse, save, describe})` from `features/drafts/savers.ts`, which registers the saver and returns `put(data: T, id?)` and `read(draft)` bound to that kind; `useKindDrafts(kind)` reads its drafts in a component with typed data, and `DraftBadge` goes beside anything drawn from one. `put` throws `DraftTooLargeError` for data too big to keep and `DraftBusyError` while the draft is being saved. A browser can be shared, so `owner` records who made each draft: the account (`accountIdentity(me)`, `person:` and the account's id), or the signed-out visit (Decision 0022). A visit is a random value in the tab's `sessionStorage` (`fieldclub.drafts.visit`), kept through a reload and a provider's round trip, and started afresh whenever a signed-in person leaves the tab: a sign-out, a ban, the session running out or another account (`setDraftsViewer`). `useDrafts`, `listDrafts` and `useKindDrafts` give only the viewer's own drafts: the signed-in account's, or, signed out, this visit's made in the last 24 hours (`isViewersDraft`). So the map, "Your marks", `/mark/:draftId`, the scan and the second-look cards never show anyone else's. `useAllDrafts` and `listAllDrafts` are for the drafts bar and the account page. Drafts kept under the account's creation time, which identified accounts before `Me` had an id, become the person's own when they sign in (`adoptFormerDrafts`). The sign-in sheet notes in `sessionStorage` (`fieldclub.drafts.signin`) that a sign-in started in this tab, and how: a provider's button, an emailed link asked for, or the development sign-in (`noteSignInStarted`). Only a sign-in that finishes in the same tab, the same way, within 30 minutes takes over that visit's drafts (`adoptDraftsAfterSignIn`): a provider's comes back as the page loading signed in, and the others finish in the page (`onSignedInHere` in `session.ts`). The emailed link's page forgets the note when the server answers `asked_here: false`. A page that loads already signed in, or hears of a sign-in from another tab, takes over nothing. Every adopted draft is `held` until the person presses "Send" or "Send all" in the drafts bar, or "Send it and see how it compares" on a second look's card (`sendHeldDraft`), because someone else may have used the tab before them and an answer is final (Decision 0024). Once the person is ready, every waiting draft of theirs with a saver that isn't held is saved exactly once: one run at a time in a page, a Web Lock across tabs, and a claim on each draft in storage. A saved draft is removed, unless it was changed while it was being sent. A failed one stays with its reason. Drafts that aren't the viewer's own are never saved unasked: the drafts bar shows them by kind alone, without their description, and offers "Save as mine" to someone signed in and "Discard" to anyone. Signing out with drafts in the browser asks whether to keep them, and deleting the account discards them unless told not to. An unreadable store is copied aside under `fieldclub.drafts.unreadable.<time>`, an older version is migrated (version 2's browser-wide epoch is dropped, so its signed-out drafts are nobody's until claimed), and a newer build's store is left alone. When the browser won't store everything, what it refuses stays in memory and the rest, removals above all, is still stored. Fixture mode registers one stand-in kind, `fixture_probe`, for the end-to-end tests. Findings and second looks register theirs, described below.

<!-- Marking and Explore (f1/findings). -->
`features/findings/` holds the findings data the other features share: the request functions, one set of query keys (`findingKeys`, all under `["findings"]`, so a save invalidates the map, the list and any page at once), the response types taken from the generated schema, the filters, and the finding last chosen. The Explore panel at `/` lists the findings in view from `GET /findings?bbox=`, a page of 30 at a time with a "Show more", newest first, at every zoom. It asks for the same snapped box as the map's markers, after the same pause, and with the same filters for step, state and class. The map fetches ruled-out findings and hides their layer, so its switch acts at once, and the list leaves them out of what it asks for while they are hidden, so the two always agree. A finding whose position the viewer may not see is listed by its one-kilometre square. Choosing one, from the list or by clicking its marker, opens `/f/:id` and marks it on the map, as a ring or as its square. When the list and the map's findings layer both fail, either one's "Try again" tries both. Closing any panel goes to the bare map.

"Mark a finding" opens `/mark` with the drawing tool started and nothing placed, so the map takes taps at once. Each tap or click adds a point at the active end, a tap on the far end of three points or more closes the shape, and a drag on a point's handle moves it. "Add a point at the cross" in the drawing bar is the keyboard's way to add one. One point is sent as `location`, and two or more as a `path` with no `location`. The drawing bar, the selected-point bar, the handles and the guidance are described in `docs/UI.md` ("The drawing tool") and the path in [the findings area doc](architecture/findings.md). On a phone, while points are being added, the sheet rests at its peek stop and a compact drawing bar takes the primary action's place. Once drawing stops the sheet opens half-way, and the map moves if need be so the anchor stays above it. The form asks for a class, from `/meta` with its pictogram, and offers a period (not known by default), a title (the class and its one-kilometre square, such as "Enclosure in SU 10 69", or "Moat in J 33 74" on the Irish grid, when left blank, because a title is shown to everyone and the client can't know the level the server will set; it holds no run of three figures, no dot and no slash, so the server's `position_in_text` can't refuse it, which `compose.test.ts` checks across both grids), and a note. `view_state` comes from the map store. A class whose `sensitivity` in `/meta` is above open gets a sentence saying who will see its exact place, and the form ends with the finds notice, taking the reporting route of the nation under the mark from `notices.find_reporting`, with a link to the scheme where it has one. Signed in and ready, a save shows the mark at once, sends `POST /findings` and opens the finding's page, or takes the mark back and says why in a toast, keeping the form. The toast offers "Try again" only after a failure of the network or the server: a refusal of what was sent, such as a place outside the covered area, would be refused again, and the form says what to change. Every save carries a `client_ref`: a draft's own id, or for a save made at once one reference per mark, which "Try again" sends again, so a save the server made but whose answer was lost isn't made twice. Otherwise the finding becomes a draft at `/mark/:draftId`, drawn on the map as a dashed ring with a "not saved" sign, and the sign-in sheet opens. After sign-in the drafts machinery saves it, and if its panel is open the finding's page replaces it. Features reach the main MapLibre map through `map/mainMap.ts` and draw their own marks over it in DOM and SVG positioned with `map.project`, re-rendered as the map moves (`map/useMapFrame.ts`), so they never change the map's style.

`pnpm e2e` runs the end-to-end tests in fixture mode, on Vite at `FIELDCLUB_E2E_PORT` (default 5199). `pnpm e2e:full` runs `frontend/e2e-full/` against the real backend. It builds the interface into a folder of its own in the system's temporary directory, creates a database called `fieldclub_e2e_<pid>` on the development PostGIS server, starts the backend in the test environment with the development sign-in on (port `FIELDCLUB_E2E_API_PORT`, default 6198), which serves the built interface as production does, with its security headers, and drops the database at the end. Every test fails on a `Content-Security-Policy` violation in any page it opens (`e2e-full/support/policy.ts`), and `policy.spec.ts` proves the check sees one. Outside tile services and terrain tiles are stubbed. The sign-in sheet offers the development sign-in only when `/meta` says `auth.dev_login: true`, which this backend sends because its development sign-in is on. The backend's output goes to a log file, where `e2e-full/support/inbox.ts` reads the emailed sign-in links its log mailer writes. `GET /auth/dev-outbox` gives the same links without the log, for the tests to move to, so the emailed link is tested end to end in the browser that asked for it and in another. Add a spec for any flow fixture mode can't prove. CI runs both suites, the second in a job of its own with a PostGIS service.

<!-- A finding's page (f1/findings). -->
A finding's page, at `/f/:id`, lives in `features/finding/`. Its query keys are in `keys.ts`, all under `findingKeys.detail(id)`. The head shows the step as a badge and the meter, with the ladder's steps named beneath it and this finding's marked, the state and its reason when the finding isn't open, who found it and when, the class, the period, the nearest place that `GET /geo/point` names for the position the viewer is shown, and the grid reference. The distance to the place is given only for an exact position, because one measured from the middle of a square would look more exact than the square is. A square is written spaced like a grid reference, "SU 10 69", wherever the frontend shows one (`findings/square.ts`). Once answers are visible it also shows the class other people agree on. Someone sent the square instead of the place sees the square and one sentence on why, with sign-in offered for a protected finding. Opening the page marks the finding on the map and moves the map to it, unless it is already in view close in, so a link that carries a view keeps it. "See it as the finder did" applies the finding's `view_state`.

"What would move it up" renders the assessment's `next_steps` in the server's words. Each step gets a button for what this person could do: a second look, the form for each evidence kind that would meet it, the evidence waiting on an endorsement, or a link to share for the finder. Which steps a second look meets, and which evidence kinds meet the rest, come from `/meta`'s `vocab.next_steps` (`stepRule` and `isAnswerStep` in `describe.ts`, which help wanted uses too). An evidence step that names its missing strands offers only their kinds. A step code `/meta` doesn't name gets its prompt and no button. `parseMeta` refuses a document without the rules, because which steps are blind rests on them. The client restates no threshold of the ladder.

What the viewer may do comes from the finding's `actions`, which the server works out by running each route's own checks (`positionOf` in `describe.ts`): answering, adding evidence, commenting, editing, withdrawing, raising the level, lowering it through the moderation route and verifying, and on each evidence item voting and verifying it. The client reads no role. A signed-out visitor is told `unauthorised` for everything, and someone who owes the welcome step `onboarding_required`, so `offered` treats those two reasons as "once they sign in": the page offers the action, and pressing it asks for sign-in first or keeps a draft. Work that needs the exact place is offered only on a finding the server sent exactly and that isn't withdrawn. The finder's own words ("Your finding", the reason there are no vote buttons) come from comparing handles. The sentences that say who sees a finding's exact place at each level (Decision 0005) are still the client's (`whoSees`), a known gap until `/meta` has them. A change of step or state, from any cause, animates the meter, swaps the badge and is said in a live region.

The second look on the page is offered to anyone the server lets answer, or would once they sign in. It goes in two steps (Decision 0008, point 8). The answer is one of three buttons, and one press sends it at once, alone, as `PUT .../observation` with `detail_follows`: it counts, and the reply reveals nothing. The page shows "your answer is in" at once and takes it back with a toast if the server refuses it. The optional detail follows (`secondLook/DetailStep.tsx`): what they think it is, and whether each ordinary explanation could account for it, and a note. One button, "See how it compares", sends the detail, or nothing, as `POST .../observation/reveal`, and its reply is the reveal. Until then the person has seen nothing of anyone else's answers, so the class they give counts as unprompted. Someone who leaves between the steps finds the detail offered again, because the page gives them `my_observation` with `revealed: false`. The page holds the held answer as its own and leaves the tier and score as they were until the reveal shows the move. The reveal appears in a live region that is on the page, empty, before the answer, so it is read out, and the panel scrolls to the section's heading, which takes focus in place of the button that went. When another tab had already revealed the answer with other detail, the server refuses this detail (`answer_final`), so the reveal is asked for again with none, shown, and a toast says the detail added here wasn't kept (`revealAsAsked` in `finding/api.ts`, which the queue uses too). After the reveal the answer isn't said a second time below it. The class question starts with nothing chosen, and its empty choice is "Don't know", so it never reads like the answer "Not sure". On a phone, the finding's title keeps to one line while the detail is asked, and the line under the button stands above it rather than in the bar that stays in sight, so the half-open sheet leaves room for the detail. "Give a second look" brings the sheet to half-way, from fully open too, and the map pans if it must so the place is above the sheet; the detail step does the same once as it appears (`secondLook/useAnswerInSight.ts`). Other people's answers and the counts arrive only in the server's reply, and the answers list is asked for only when `answers_visible` is set. After the reveal, only the note can change, and the answer can be taken back and counted again; one taken back before its reveal is counted again still waiting for its detail. A signed-out answer is an `observation` draft, defined in `secondLook/answerDrafts.ts`. The press keeps the answer as a draft and offers the detail; "Sign in to see how it compares" adds the detail to the draft and opens the sign-in sheet. After sign-in the drafts machinery sends them in order: the answer alone, then, if the person asked to see the comparison, the detail with the reveal. A draft from an earlier build, whose answer and detail went in one request, is read as one that asked for the reveal. What saving it revealed, or that its answer waits for its detail, is shown only by a page for that finding opened before the save, once, and the page then asks for the finding again rather than taking the reply's copy. The answer buttons, the detail step, the reveal and the draft kind are in `secondLook/`, and the blind queue uses them too.

Evidence is grouped by kind, with its stance, contributor, how many people endorsed and disputed it in words ("Endorsed by 2 people and disputed by 1.", from the item's `endorsements` and `disputes`) and, for the kinds `/meta`'s step rules verify, verification. A vote shows at once, but the counts wait for the server. Vote and verify buttons follow each item's own `actions`. Where the server refuses a vote, there are no vote buttons, and on evidence the person added, or on evidence about their own finding, a line says that others endorse or dispute it. The chooser of evidence kinds says what each kind is beside it, from `/meta`. Each kind has its own form. What each form asks for is in `evidenceForms.ts`, which mirrors the backend's rules until `/meta` says. Before a site visit, survey or dig is logged, the form shows that nation's field-visit rules from `/meta`. A ground photo is uploaded by `photos/PhotoUpload.tsx` as soon as it is chosen, and its id goes with the evidence as `media_id` (see "Profiles, reporting, moderation and photos" below). Linking a heritage record offers the server's suggestions with source and distance, a search of the index, and a record from a link-only source by identifier and address alone. The link-only sources are those in `/meta` whose `access` isn't `bulk`. Comments, votes, follows and new evidence show at once and are taken back with a toast when refused. A comment a moderator hid is shown to its author and to moderators with a line saying so, because only they are sent its body. Edit, withdraw, raise the level and lower it are offered exactly as `actions` allows. Lowering goes through `PUT /mod/findings/{public_id}/sensitivity` with a reason for the moderation log. The server refuses a title or description that says where a finding that isn't open is more closely than its square (`position_in_text`, naming each field). The edit dialog and the mark form say so beside each field named, in words that say what to take out (`positionInText.ts`), and the first field named takes focus, and a finding draft refused for it after sign-in keeps the fields in its failure so the form does the same. Free text with a position the viewer may not see arrives with `[position hidden]` in its place and is shown as it comes. Everyone can copy the link and download GeoJSON or CSV. `Slots.tsx` holds the report button's place beside the step badge, on each comment and piece of evidence, and on a photo.

A finding's mentions live in `features/mentions/`, with their query keys in `keys.ts`: a finding's under `findingKeys.detail(id)`, so whatever refreshes the page refreshes them, and the recent feed's under `["mentions", "recent"]`. The page lists `GET /findings/{public_id}/mentions` newest first, each with its title linked in a new tab, a YouTube or Vimeo video at its start time (`mentionHref` in `describe.ts`, which links only http and https addresses), its kind from `/meta`, its author and date, and who added it or that the channel scan found it. A picture is shown only from https, without sending a referrer, and a pictogram for the kind stands in for none or one that fails to load. Adding one looks the address up first with `POST /mentions/preview` and shows what was found, then offers the kind it looks like, the start time and a note. A preview that was refused or failed, or a lookup that failed for any reason but the address, still lets the mention be saved by its address alone, and says so. A new mention shows at once while the form stays where it was, busy, and is taken back with a toast, the form kept, when refused; a new try takes the last failure's toast away. Once saved, the mention is brought into view with focus on it, and a status line says it was added. An address changed after a lookup drops the kind and start time it found; `mention_exists`, `mention_hidden`, `invalid_address` and a map link refused on a finding that isn't open (`position_in_text` on `body.url`) are said beside the address. A mention whose address the server withholds from this viewer (`canonical_url` null) shows its title with a line saying its address goes only to people who see the finding's exact place. Its adder, matched by handle, can remove it, with a button named for the mention; focus then goes to the next mention, or the one before, or to adding one. Both lists are asked for once more after a failure that may pass, and not after a refusal. Adding is offered with the finding open and comments allowed, after sign-in. `/mentions` lists `GET /mentions/recent` with each mention's finding as the viewer may see it: an obscured one by its square, selected on the map as that square. It belongs to the Activity mode, whose page links to it until the activity feed is built.

The follow-up timeline on a finding's page (`finding/timeline/`) is a second view of its evidence: the items whose kind is in `/meta`'s `field` or `official` evidence group, the kinds the server logs as `followup_logged`, ordered by `occurred_on`, or the day they were added when they have none. Each shows its date, kind, title, who did it and who logged it, its outcome, verification or stance, its note and its link. Which entry moved the finding up is read from `GET /activity?finding=&kind=followup_logged&kind=tier_changed`: a step up by the same person within a minute after a follow-up, with no other follow-up between, is put down to it, because the server reassesses in the request that adds the evidence. "Add to the timeline" offers the follow-up kinds and opens the evidence section's own form for the one chosen, so a visit gets the field-visit rules first. The chooser (`evidence/KindChooser.tsx`, shared with the evidence section) brings itself into view with focus on its heading; Cancel and Escape give focus back to the button that opened it, and the form that opens takes focus on its heading. Each entry's link is named for its kind and date, and, like an evidence item's, goes through `safeHref`, so only an http or https address becomes a link.

A link made by `stepLink.ts`, `/f/:id?step=<code>&strand=<strand>`, opens the page with the form for that next step ready: the page finds the step among its own next steps, picks the button it would offer this viewer (the strand's evidence form when a strand is named), presses it once, and takes the request out of the address. A step met since the link was made opens nothing.

<!-- Second looks and help wanted (f1/findings). -->
Second look, at `/review`, lives in `features/review/`. It is blind (Decision 0008). The panel asks `GET /review/next` for ten cards at a time, from where the map was when the queue opened (`queue.ts`, rounded to about 100 m), and shows one. Before an answer the browser holds a card's public id, place and view and nothing else: no title, class, description, tier or count is asked for, kept or shown. The panel's title and the page title are the same for every card, the address stays `/review` with only the map's view after it, and moving between cards adds no history. While `/review` is open, `ReviewLayer` holds the findings overlay back through `map/hiddenFindings.ts`, so the map neither asks for the findings in view (whose GeoJSON carries titles and classes) nor draws their markers, from the moment the queue opens, not only once a card is up. When the queue opens it also drops every findings query, every help wanted query, the recent mentions feed, the activity feed and the notifications from the cache (`review/forgetClaims.ts`), because those browsed first at the same place would hold the claim of the finding a card turns out to be. The notifications are not asked for again, by their timer, a live event or a resync, until the queue closes, so the unread count is not shown during it (`useUnreadCount`). The heritage records overlay, the live sources' records among it, is held off the map from the moment the queue opens until the card is answered, because a scheduled monument's square at the spot would answer the question the card asks (Decision 0015): `ReviewLayer` holds it through the map store's `held` list (`map/heldOverlays.ts`), which `overlayShown` reads, and the person's switch is left as it was. For each card it moves the map to the place in the finder's view once (`seeViewAt` in `finding/mapView.ts`), after the panel or the sheet has stopped moving (`whenStageSettled`), and draws a frame of four corners round the place, open in the middle. A finding's page waits for the same before it moves the map. The layer is mounted by the shell, so all of this holds while the layer panel is open over the queue.

`reviewStore.ts` keeps the current card, the answer on its way and the answer the server holds for its detail (`held`, with whose it is), the detail being given, what the reveal showed and the cards answered or skipped in this visit, outside the panel, because the shell unmounts the route's panel while the layer panel is open. A card is answered in the same two steps as on a finding's page, through `useCardAnswers` in `useReviewQueue.ts`: one press of the shared answer buttons, or the keys 1, 2 and 3 (`useAnswerKeys.ts`, which ignores them in a text field, in an open dialog and with a modifier held), sends the answer, then the detail step offers the detail and "See how it compares". Each card's question takes focus as the card appears, unless focus is somewhere else on purpose or the page has only just loaded. After an answer pressed, focus goes to the line saying it is in, so the detail is read next; after one given by its key it goes to "See how it compares" once the answer is in, so a number and Enter answer a card. Someone who leaves the queue between the steps and comes back finds the detail offered again. The card is kept in `sessionStorage` while its answer waits for its detail, so a reload comes back to it too, and it is shown again only to the account that answered. The heritage records stay held off the map between the steps. On a phone, the detail step brings a fully open sheet to half-way and keeps the place in sight, and "Next finding" and "Skip this one" bring it down before the map moves to the next card. The reveal shows how the answer compares, whether it moved the finding up, and the finding in full, with focus on "Next finding", which the comparison describes so it is read out with the button. Skipping sends nothing. The queue steps past cards answered, skipped or waiting as a draft; a used-up page leads to the next, and the top is asked for again once before the queue is called empty (the server pages by offset, so answers move cards between pages). An empty queue offers scan a square and help wanted, and the skipped cards again. Signed out, the press keeps the answer as an `observation` draft through `secondLook/answerDrafts.ts`, which can be changed until it is saved and replaces itself rather than adding a second, and the detail is offered as on a finding's page. The card is kept in `sessionStorage` while its answer is waiting as a draft too, so a provider's sign-in returns to it. It is read back only while that draft is still there, and a copy that isn't wanted is removed on load. When the drafts machinery has saved it, the card shows what it revealed, or offers the detail if the person hadn't yet asked to see the comparison. An answer sent at once, signed in, discards any draft answer to the same card that failed to save.

Help wanted, at `/help`, lives in `features/help/`. It asks `GET /review/tasks` for every group at once, fifty tasks each, and offers the work by kind (`kinds.ts`): second looks, one kind for each strand of desk evidence in `/meta` (old maps, aerial photos, heritage records and so on), the evidence group split by each task's `missing_strands`, going to look on the ground, and finding it on record. The strands are those of the evidence kinds that `/meta`'s rule for `need_strand` names, and the steps a second look meets are the ones its rules say. Each kind has a plain name and a line on what the work is, written in `kinds.ts` because `/meta` has no words for step codes; a step code the build doesn't know is still listed, under the server's own prompt. Second looks go to `/review` and are never listed by finding, whatever the address. Any other kind opens `/help/:kind`, a list paged by the group's cursor, each finding opening its page with the right form ready through `stepLink.ts`. A strand's count is what the loaded page holds, said as "or more" when the group has more pages.

<!-- Records and search (f1/records). -->
`features/records/` shows the record index. The records overlay draws both layers of `/tiles/records`: `records` as small squares by category for point records, thinned below zoom 15 so that no two squares touch (a village's listed buildings otherwise merge into one block over the earthworks round it), and from zoom 15 as a hairline outline over the faintest fill for records with an outline, so the earthwork inside stays in sight (drawn from zoom 12, Historic England's half a million aerial-mapping outlines netted the terrain over and cut the frame rate while panning by two thirds); and `record_counts` as squares numbered with their count when the map has glyphs, which never overlap, the bigger count winning where two would touch. A tile carries one or the other, so the map draws whichever it gets. Below zoom 12 (`RECORD_FEATURES_FROM_ZOOM`, the backend's `FEATURES_FROM_ZOOM`) every tile holds counts, and those are drawn only while the map store's `showRecordCounts` is on: the Layers panel's "Counts when zoomed out" switch under the records, off by default and carried in the address as `rc=1`, which an address that names a place or a view without it turns off. While it is off and the map is out that far, the records row says that records are shown from closer in. A busy tile from zoom 12 up holds counts in place of its records, and those (`records-counts-busy`) are drawn whenever the records are. A count's layer that is switched off is never hit by a click. The layer panel's chips turn categories and sources off through `map.setFilter`, held in `useRecordFilters` as the lists of what is off. Sources are listed under the category they fill, folded away, each category with "All" and "None"; a catalogue source of another kind, such as boundaries or place names, isn't offered. A count stays while any source it names is still on. A point record whose `precision_m` is 1000 or more gets no square: when the main map comes to rest, the records in its loaded tiles that are placed only to a square are drawn, in both panes, as that dashed square from a GeoJSON source (`impreciseSquares` in `features/records/shape.ts`, the same square the record's page draws). Clicking a record opens `/r/:id`, clicking a count zooms in two levels, and a right click opens `/elsewhere` for that spot. Findings sit above records: a click on a finding's marker opens the finding even with a record under it (`map/findingHits.ts`), while a record's marker inside an obscured finding's square opens the record, because the square is only an outline. While a finding is being marked, or a map tool such as the height profile has the clicks, neither opens anything. When the main map comes to rest it reports which stored sources it is drawing, and the credits name only those (`features/records/onScreen.ts`). Until it has reported, every source is credited. A click inside a record's area opens it, except an area that fills the whole view: some records are the extent of a survey, the size of a county, and would take every click made within them. Such a record is opened by its outline, and whatever lies under it is reached through it (`recordTarget`, `spansView`). A record's page goes to the record when its middle is out of sight, unless a click on the map opened it, when the map stays where the person clicked (`OPENED_FROM_MAP` in `paths.ts`).

`/r/:id` shows a record from `GET /records/{id}` with its source, licence, attribution and a link to the original, and lists the findings linked to it from `GET /records/{id}/findings`, each with its pictogram and its step in words. Every link from an outside source goes through `safeHref` in `map/attribution.tsx`, so only http and https addresses become links, and every name is rendered as text. The open record is drawn over the map. A record with `precision_m` of 1000 or more is drawn as its square, dashed, and never as a point. `/records` searches `GET /records/search` by words, scope (the map's view or everywhere), category and source, each filter a repeated parameter (`apiUrl` sends a list that way), a page at a time, and links the same search as a GeoJSON download that carries each record's licence. The search lives in its address, `/records?q=&scope=everywhere&category=&source=` with the API's names (`features/records/searchAddress.ts`): typing replaces the history entry, any other change adds one, and an address with no search is given the one kept from earlier. Each result names its source and licence. Record names are shown with HTML entities such as `&amp;` decoded (`features/records/text.ts`), since some sources send them that way. `/elsewhere?lon=&lat=` lists `GET /context/links` for a spot, or for the middle of the map without one, each under the `title` the server gives it, grouped by what each viewer `shows` (LIDAR, old maps, aerial photographs and so on), the most local first within a group and each naming the area it covers, each opening in a new tab with `rel="noopener noreferrer external"`. Links the catalogue doesn't mark `verified: yes` say they weren't checked.

`features/search/SearchBox.tsx` is the search field in the shell. It is an ARIA combobox over `GET /geo/search`, asked 250 ms after typing pauses once there are two letters (Enter asks for one), with the request cancelled when the text moves on. Results are grouped by kind. The arrow keys move through them, Enter takes one, and Escape closes the list or clears the field. Choosing a result moves the map there and opens a record's or a finding's page; a record's ref must be a record id before it becomes an address. Enter before choosing takes the first result only when it is a grid reference, coordinates, a finding's id or a place named exactly what was typed, and otherwise opens the list, since a record that only shares a name can be anywhere. The list grows to the foot of the uncovered map and scrolls with a shade at the end it can scroll towards. "Try again" and the last option, which opens the record search with the same words, stay at its foot, under them the name and licence of each source the results came from. Both search fields stop at the server's 200 characters, and a search the server refuses (422) is answered with no retry.

Live sources (Decision 0007) are asked by the browser in `features/records/live/`. Each starts off in every page load. The catalogue comes from `GET /context/live-sources` once someone opens the layer panel's "Live sources" section. A source whose pattern takes a box or a point, whose address is https on another site, whose `answer_format` this browser has a reader for (`geojson`, `ads_search`, `mediawiki_query`), and which the server marks `shown` with a `credit` and a link template is offered. The server sends only the sources it shows, so the check guards against an older server. One that asks for a single record id isn't offered. A source on shows the server's `credit` and `licence_label`, never the catalogue's research notes in `attribution` and `licence`, and says that each record links to its page at the publisher, named as a link to its `homepage` where there is one. Where the terms ask for a credit or licence taken from each record, each listed record shows it, read from `preferred_credit_field` when the record has it, otherwise `credit_field`, and `licence_field`, dotted paths in which a number indexes a list, as plain text with any HTML taken out (`live/parse.ts`). Once a source is on and the map rests at its `min_zoom` (13 when the catalogue gives none) or closer, it is asked once for that view, with its `limit_param` set to one more than the map draws and no more than its `max_limit`, straight from the browser with no cookies, and the request is cancelled if the view changes first. It has 12 seconds to send its whole answer and at most 5 MB, read as it arrives whether or not it states a length. Nothing is retried. A source that fails or that the browser can't read is turned off and says why. Each answer is read by the reader for its format, and a record's name and id only from the catalogue's `name_field` and `id_field` (dotted paths), never guessed; an answer that doesn't fit its reader is unreadable. At most 200 records per source are kept, and a source that says it held more back (ArcGIS's `exceededTransferLimit`, the ADS `total`) is reported as cut short. They're drawn as hollow squares, listed in the layer panel with their links, credited, and never sent to OpenAntiquity's server.

<!-- Investigations (f2/notebook). -->
`features/investigations/` is the shared notebook. Its requests are in `api.ts` and its query keys in `keys.ts`, all under `["investigations"]`. `/investigations` lists, under a one-line explanation and a "Start an investigation" button that opens the title field, the person's own (`scope=mine`), the invitations waiting for them with accept and decline (`scope=invited`), and the public ones, all of them or, with a switch, only those whose area meets the map's view (`bbox`, rounded outwards to about 100 m); which list and the switch are in the address (`?list=` and `?inview=1`). Signed out, the first two say an account is needed and ask the server nothing. Starting one takes a title alone and opens it. `/i/:id` shows the title, the owner, the visibility, the summary and the notes, then the items in the owner's order, who works on it, its area, who can see it, the downloads and deleting it. Notes, and every item's own note, are read with a small Markdown parser of its own (`notesSyntax.ts`: headings, paragraphs, lists, strong, emphasis and links; every block pattern is anchored with a fixed prefix, and a heading's closing hashes are stripped with string operations, so a line takes linear time whatever it holds) into plain data that `Markdown.tsx` renders as React elements, so HTML in a note stays as the characters it is, and a link becomes one only for an http or https address (`safeHref`). Notes come from other members and are read signed out, so the parse takes time in proportion to the note's length whatever it holds: each search for a closing marker or a link's `](` is remembered for the rest of the paragraph, every look ahead draws on one budget of 40 characters per character of the note, after which the rest is shown as written, emphasis nests at most eight deep, and an address is at most 2,048 characters. Each kind of item is drawn for what it is: a finding with Explore's `FindingLink`, as the viewer may see it; a record with its category and compact credit; a saved view with its grid reference and layers and "Show this view", which restores the layer, the comparison layer, the light, the tilt and the place through `seeViewAt` (`savedView.ts`); a height profile with the profile panel's chart and a link that opens it on the map; a reference, whose link is named by its title and its site; a note. An item the server sends with `unavailable` is its kind and one line saying why, with none of its title, note or who added it, and can be moved or taken out but not edited. A saved view or height profile held back as `near_protected` keeps its title, which the server has cleared of positions, under the line saying it is near a protected finding. When the notebook holds a finding the viewer sees only as its square, a note under its summary says that views and profiles near it are held back, its area is shown as whole 1 km squares, grid references in it are hidden, and that what is hidden is kept when the viewer edits. The order is changed by dragging an item's handle (pointer events, so touch works, with the panel or the sheet scrolling while the pointer is within 40 px of its edge, `dragScroll.ts`), by the arrow keys, Home and End on the handle, which keeps focus, and by the up and down buttons; on a touch screen the handle and the buttons are 44 px. Each move is said in a live region, shows at once, and is sent as "after this item" in the order made, one request at a time per investigation (`useInvestigation.ts`), naming the nearest item before it that the server has, never one still being added. A refused move says why in a toast, and once no move for that investigation is waiting the server's order is asked for and shown. Adding and editing items, and every change to the investigation, are shown at once and taken back the same way. Taking an item out hides it at once, through the items query's `select`, so a refetch can't bring it back, and offers "Undo" in a toast for six seconds; the request goes when the toast does, or when the page closes or is left (`pagehide`). Focus moves to the next item's handle, or to the list's heading. Every dialog gives focus back to the control that opened it, also when it is taken out of the page rather than closed (`ui/Dialog.tsx`). What each person is offered follows the server's rules (`describe.ts`): the owner and editors change the contents; only the owner changes visibility, invites, removes and deletes; a private investigation explains that inviting needs it public or unlisted first and offers no invitation, and private is offered back only while the owner is the one member, invitations counted, so not while the members are loading or couldn't be loaded (Decision 0009). Publishing, making it unlisted or private, removing someone, taking back an invitation, leaving and deleting each ask first, publishing with one sentence on what it means and, for one with no area, a sentence saying it won't be listed by place with "Use the map's view as its area". Someone is invited as an editor or a reader with a `ChipGroup`. The downloads are the export's three formats; the report opens in a new tab. The open investigation's area is drawn on the map as a dashed outline over the faintest fill, under the findings (`useAreaOnMap.ts`, from `MapView`), and the page frames it once, after the panel settles, unless some of it is already in view. Editors set the area to the uncovered part of the map's view, or take it off. "Add to an investigation" (`AddToInvestigation.tsx`) is on a finding's page (not a withdrawn one, which the server refuses), a record's page, the height profile and the layer panel (the map's current view, kept as `savedView.ts` captures it). It asks a signed-out person to sign in first, then offers the investigations they own and those where they are an editor, and a new one by title, with an optional note. A new one started but whose item couldn't be added stays chosen, so trying again adds to it. The list doesn't say a member's role, so the page of each one they don't own is asked for it. Fixture-mode tests answer every investigation route from one in-memory stand-in that keeps the server's rules (`src/test/fixtures/investigations.ts`), shared by Vitest and Playwright.

<!-- Scan a square (f2/notebook). -->
`features/scan/` is "Scan a square". Its requests are in `api.ts` and its query keys in `keys.ts`, under `["squares"]`, except the person's own findings in a square, which sit under `["findings"]` so a saved finding asks for them again. `/scan` asks `GET /squares/next` once, near the middle of the uncovered map rounded to about 100 m (`nearFrom` from the second-look queue), with `exclude` naming every square passed in this visit and every square waiting as a draft, the newest 100, the drafts last so they are kept first. A square offered that this browser has already done is passed over and asked again, up to three times (`nextSquareNotDone`). The square lives in `scanStore.ts`, outside the panel, so the layer panel or marking a finding over it doesn't end the scan, and the store is kept in `sessionStorage` so a provider's sign-in comes back to the same square and the visit's count. `ScanLayer`, mounted by the shell, frames each new square once, after the panel or the sheet has settled, so it fills 80% of the uncovered map's narrower side with room left for "Mark a finding" below and, while there are drafts, the drafts bar above (`frameSquare` in `square.ts`), north up and flat. Going from the scan to marking a finding and back keeps the ground in the middle of the map where it was (`keepMiddle`), because on a phone the sheet drops from half-way to peek for marking, which would otherwise move the cross that "Add a point at the cross" uses out of the square. That ground is taken in the render that changes the stage, before the shell publishes its new cover, and every change of cover brings it back to the middle at once, until the person moves the map, places the first point or leaves; "Add a point at the cross" pressed before the map has caught up puts the first point on it. Coming back frames the square again only when less than half of it is in sight. While there are drafts the bar above takes room, so a square still framed as it was when the first draft appeared is framed again. Marking opened from the scan sets `features/mark/markReturn.ts`, so saving the finding, keeping it as a draft or closing the marking panel goes back to the scan, and the panel offers "Back to the square"; a finding saved this way says so in a toast with "Open it". While `/scan`, or marking a finding opened from it, is on screen, `useScanOnMap` draws the square on both panes as an outline in `--accent-strong` with the ground outside it shaded in `--bg` at 38%, under the findings' markers. The panel names the square and how many people have scanned it, and ends it with one of three presses. "Nothing obvious" and "I marked something" count at once. Once something is marked in the square, "I marked something" comes first as the primary button. Both wait, with a line saying so, while the terrain is still being prepared (`useTerrainLoading`), since neither should be said of ground not yet seen; a skip doesn't wait. Signed in and through the welcome step, the result goes to `PUT /squares/{ref}` with the whole seconds spent, and a refusal takes it back with a toast. Otherwise it is a `square` draft (`squareDrafts.ts`), which replaces an earlier draft for the same square and is saved after sign-in. "I marked something" is offered once a finding counts towards the square: a finding draft placed in it since it came up (`kmSquareAt` names the square), or one of the person's own findings that `GET /findings?bbox=&author=` lists in it, dated no more than five minutes before it came up, for clocks that disagree. A skip asks for the next square at once. Signed in it is sent too, for the ranking, and signed out it is only left out of the visit, since a skip says nothing about the square. A result shows "Next square", which takes focus. The visit's count of squares looked over is the only reward. The panel says when there is no square left within 50 km (`no_square_available`), when the server is busy (429 or 503; any other failure says what happened and offers "Try again"), and when `GET /terrain/coverage` has no tile under the square's centre, which offers another square and records nothing.

The scan coverage overlay from `/meta` is filled from `GET /squares/coverage` for the main map's view, pushed out to a 0.02 degree grid, while the overlay is on and the box is at most 2,500 km²; a wider view asks nothing, clears the layer and says to zoom in, in the layer panel and in the scan panel, which offers the overlay's switch too. The squares are shaded in `--accent` from 10% for one scan to 25% for ten, and from zoom 12 carry their count where the map has glyphs. A failed request turns the overlay off with the layer panel's notice and "Try again". A result saved, at once or from a draft, asks for coverage again.

<!-- Map layers and terrain tools (f1/records, stage 2). -->
The layer panel begins with the switch for the map drawn over the terrain, the `openmaptiles` overlay, since it is the one most often wanted off. The other overlays are listed lower down. The layer panel lists the views by group, the default view first in its group, each with a preview: one tile of the view's own `/meta` address at the catalogue's opening spot, or for raking light a hillshade the browser draws from the elevation tile there with the current sun. The view that is on and each overlay that is on show their attribution and, as a link to its terms, their `licence`, unless the attribution already links the licence by name. Nothing in the frontend builds a tile address: every one is a `/meta` template filled in, and `map/tileRefresh.ts` asks for `/meta` again every half hour and when the page comes back into view, and gives any source whose addresses changed, such as a new `?v=` token on a terrain view, the elevation or the records tiles, its new ones with `setTiles`, which reloads it without rebuilding the map.

`features/layers/` holds the terrain tools. `/profile?line=lng,lat,lng,lat,...` is the height profile: clicks on the map, or "Add a point at the cross" for the keyboard, add points to the line in the address, which `POST /terrain/profile` samples about once a metre (at most 1,000 samples, so short lines are read from the 1 m grid). The chart is hand-drawn SVG. A marker follows the pointer, a finger or the arrow keys along the chart and the pointer along the line on the map, through `useProfileHover`. While the profile panel is open it holds the map's clicks (`map/tool.ts`), so a record under a new point doesn't open. The cross, the point it adds and the framing of a line opened from a link use the middle of the uncovered map, which the shell publishes in `map/visibleArea.ts` (`useMapCover`): the window less the rail, the side panel or the sheet, the search field and the status bar. The layer panel's query parameter, and a click on a live record, keep the rest of the address, so the line survives the layer panel opening over it. `GET /terrain/coverage` is asked for a quarter-degree box round the view from zoom 9. A pane showing a terrain view shades the 5 km grid squares in view that no coverage tile holds, and a notice on the map says so, so a blank area doesn't read as flat ground. The same notice says "Preparing the terrain here…" once the terrain source has been loading for 1.5 seconds (`features/layers/terrainLoading.ts`). Below `/meta`'s `terrain.fine_minzoom` (13 when it is absent) it says the terrain is a coarse overview when `terrain.overview.built` is true, and otherwise that only places someone has looked at closely are drawn. The coverage switch outlines where the data is and names its capture and the years the tiles in view were flown, and says the map may be blank there when a view on screen isn't loading, as coverage is what Defra publishes, not what can be drawn. The switch is left out of the permalink on purpose: it is a check on the data, and a shared view should open on the terrain, not with an outline over it. A profile with no height anywhere along it says so, and one at its 200 points says it can take no more. A tilted map has a "Back to plan view" button. With no pointer on the map, the status bar's readout, its copy button and "open elsewhere" use the middle of the uncovered map (`visibleCentre`), not of the window, and the copy button gives the server's exact reference once it has answered. On a phone the raking light control starts as its dial alone, with a button that opens the sliders.

<!-- Activity, notifications and live events (f2/people). -->
The activity feed, at `/activity`, lives in `features/activity/`. It asks `GET /activity` for 30 items at a time, newest first, with a "Show more", and can be narrowed to the map's view and to kinds of activity. "In the map's view" sends the same snapped box the map's markers ask for, widened by half a grid square, because the server matches each event by the centre of its finding's square, and waits for the map to hold still. The kinds are offered in groups (`kinds.ts`), with names written there because `/meta` has none for them, typed over every `ActivityKind` so a new kind doesn't build until it is placed. `describe.ts` turns an item into a sentence from what the server sent and nothing more: an event with no actor, which is every event a second look caused (Decision 0008), names nobody, and steps, states, explanations and evidence kinds take their words from `/meta`. A finding whose place the viewer may not see is given by its square. Each item opens its finding, marked on the map as Explore marks it, or its investigation. The filters are kept in a store outside the panel, so the layer panel can open over it. The filter bar links to "Recent mentions", which belongs to the Activity mode.

Notifications live in `features/notifications/`. Nothing is asked for, and no count is shown, unless someone is signed in. The first page of `GET /notifications` carries the unread count, which sits on the Account item of the mode rail, and on a phone on "More" and on the Account item under it, drawn small for sight and said in words in the link's name. When the count goes up, one hidden polite live region in the shell (`NotificationAnnouncer.tsx`) says the new count aloud. It says nothing for the count the page loads with, nor when the count goes down. The list is the first section of the account page. A notification is marked read once most of its row has been on screen (`useSeen.ts`, an `IntersectionObserver`), several together in one `POST /notifications/read`, and keeps its "new" mark for as long as the page stays open. "Mark all as read" sends `{all, up_to}` with the newest shown. Both show at once and are put back with a toast if the server refuses. The list is asked for again every ten minutes while the page is in view, because an invitation to an investigation has no event behind it.

`features/activity/LiveEvents.tsx`, mounted once by the shell, holds the app's one `EventSource` on `GET /events/stream`, through `liveStream.ts`. It asks for every event, with no box or finding, because a notification can be about any finding the person follows anywhere. It is open only while the page is visible and the browser online, and closed as soon as either stops. An event is a hint, never data to show: `liveRefetch.ts` invalidates the queries it could have changed, and only those on screen ask again. The feed and the notifications ask only for their first page again when the reader has paged further, and put what is new in front of what is already shown (`withNewestPage`), so reading far back doesn't multiply the requests. Each kind asks again after a short gathering wait so a burst is one request (a finding's page after 250 ms, the feed after a second, notifications after two, the map and the Explore list after five). Notifications are asked for again only for events someone else caused. `resync` refetches every query on screen except `/meta`, the session and the blind queue. After `dropped` or `closed` the stream is reopened three to six seconds later. When it ends or breaks, the browser reconnects by itself once. If that fails too, because the server is down or a proxy drops the connection, the stream is closed and treated as a refusal, since a browser would otherwise retry every three seconds for ever. A refusal before it starts, which a browser never retries, is followed by a new try after a growing wait (five seconds, doubling, up to five minutes) while `GET /activity?limit=1` is asked every minute whether anything has happened. Any reopening after the first open of the page, and return from hidden or offline, refetches what is on screen. Because a finding's page already animates a change of step and swaps its badge, a tier change caused anywhere shows on an open page as it happens, with reduced motion honoured. `onLiveEvent` lets another feature hear each event for queries of its own: an open investigations list or page (`investigations/useLiveInvestigations.ts`) asks the lists, and that investigation, again on `investigation_published`. Fixture-mode tests stand in for `EventSource` themselves (`e2e/support/events.ts`, `src/test/fakeEventSource.ts`), and the default stubs answer the stream with one that says nothing and asks the browser to wait an hour.

<!-- Profiles, reporting, moderation and photos (f2/people). -->
A person's page, at `/u/:handle`, lives in `features/people/`. It shows `GET /users/{handle}` as the server sends it: the name, the handle when it differs, the role with a sentence on what it means, the month they joined, the bio, and how many findings, pieces of evidence, comments and mentions they have. An account in the 16 to 17 band arrives with its handle as its name and no picture or bio (Decision 0009), so the page shows the handle once, as its title, with initials for a picture. Tabs list what they found (`/findings`) and what they helped with (`/contributions`), 20 at a time with "Show more". Their own page adds two tabs nobody else gets: the findings they took a second look at (`kind=second_look`), which never says how they answered, and where each of their points came from (`/points`), with the total (Decisions 0008 and 0010). Neither is asked for on anyone else's page. The words for roles are in `people/roles.ts` and the words for point reasons in `people/describe.ts`, because `/meta` has neither. There is no leaderboard. Someone else's page says that OpenAntiquity has no private messages and offers only a report button, and a moderator a link to that person in `/mod/members`. An unknown, deleted or banned handle reads "There's nobody here".

`reports/ReportButton.tsx` is the report button, rendered through `ReportSlot` on a finding, each comment, each piece of evidence and a photo that can be seen, and directly on each mention card, an investigation's page and a person's page. It names its target as the API does and is never offered on the viewer's own work or on themselves. A signed-out person is sent to the sign-in sheet first (`useRequireAccount`). The dialog lists `vocab.report_reasons` from `/meta` with each hint beside it, takes an optional note that only moderators read, and once sent says what happens next: a moderator looks, within the reason's `due_hours` where the law sets one, the reporter hears nothing more, and whoever posted it isn't told who reported it. Refusals such as `already_reported` and `recently_dismissed` are said in plain words in the dialog, which keeps what was chosen. The button is ready for mentions and investigations, which don't have pages in this build yet.

Moderation, at `/mod`, lives in `features/moderation/`. It is reached from the account page, and only by the roles that may use it: moderators and admins get four tabs, each a path (`/mod`, `/mod/photos`, `/mod/members`, `/mod/log`), and trusted members and archaeologists get the photo queue alone. Everyone else is told it isn't for them, and someone who hasn't finished the welcome step is asked to, because every `/mod` route needs it (Decision 0013). The report queue asks for each reason with a `due_hours` separately and puts those reports first, soonest due first and marked with their deadline, then the rest oldest first, each report once (`queueOrder`). Each card shows the reason, who reported it and their note, and `TargetSummary`: what was reported and on which finding, who posted it, its words, its link and its photo, and whether it is hidden, removed or gone. Upholding and dismissing need a note for the log, and upholding offers to hide the target as well. A person is banned, never hidden. The members tab lists `GET /mod/users/eligible` with where each member's points came from, who else was on those findings and how often, and "Make trusted". Below it, a handle can be looked up to change a role or ban. A banned person's page can't be found, so a handle that finds nobody offers nothing: whether the person exists, is banned or may be unbanned by this moderator is unknown until the API gives moderators a view of a user. A person banned from the lookup is offered no change of role, which the server refuses for a banned account. The log is `GET /mod/actions` in sentences, and anything still hidden can be shown again from its entry, which is the only way back for hidden evidence. On a finding's page a moderator gets Hide on other people's comments and evidence, never Remove (Decision 0013), and a Moderation section on other people's findings to hide or show the finding and to set its level, lower as well as higher, through `PUT /mod/findings/{public_id}/sensitivity`. A finding's page doesn't say whether it is hidden, so that section reads the newest log entry about it. Every moderation action asks for a reason in `ReasonDialog`, shows at once, and is put back with a toast if the server refuses. Nothing the server would refuse is offered: not a moderator's own work, not a role change or ban beyond their role. Those rules are copied from `services/moderation.py` into `moderation/access.ts`, a known duplication until the API says what a moderator may do. All query keys are under `["moderation"]`.

Photos live in `features/photos/`. `PhotoUpload` sends the chosen file to `POST /media` at once through `apiUpload` in `api/client.ts`, which uses `XMLHttpRequest` so it can report progress, with the same errors and 401 and 403 listeners as `apiFetch`. It shows how far the upload has got and a Stop button, then the uploaded picture with the sentence that it waits for approval and that only the uploader, moderators, trusted members and archaeologists see it meanwhile. A refusal is said plainly by its code (`photos/uploadWords.ts`): too large, too many pixels for its size, not an image, a kind we can't take, refused before, or the server busy. Try again is offered only when the network or the server let it down. The form waits for the upload before it sends the evidence. A photo is shown only from the address the API gives: `MediaOut.url`, `TargetOut.photo_url`, or `/media/{id}` for evidence, which carries only the id. When the server sends a photo evidence item without an id, or the image doesn't load, a placeholder says it can't be shown, without guessing why: it may wait for approval, be hidden, belong to a banned uploader, or have failed on the network. File names are isolated with `<bdi>`, so a name's own writing direction can't rearrange the words around it. The uploader's own photos are remembered in memory for the page (`photos/waiting.ts`), so their evidence can say it is still waiting. The approval queue, `GET /mod/media`, shows each photo with its uploader, size and findings, and Approve or Refuse with a reason.

The guide, at `/guide`, lives in `features/guide/`, and the about page and the notices in `features/about/`. Both are reached from the foot of the mode rail and, on a phone, from "More". The guide gives two sentences and a picture for each LIDAR view `/meta` lists, then pairs of a real earthwork and the thing most often mistaken for it, then the ladder from `/meta`'s tiers, then what to do on a visit with each nation's rules from `notices.field_visit` and `notices.find_reporting`. The pictures are small WebP files in `features/guide/pictures/`, made from OpenAntiquity's own terrain tiles. Their `README.md` says where each place is and which view it uses, and `places.ts` names the heritage records that say what each real example is and marks a look-alike no record names as the guide's own judgement, which the page says. "Show tramlines on the map", and the like, moves the map to the place in that view, flat and facing north, through `seeViewAt` once the stage has settled, and drops the phone sheet to peek first (`showPlace.ts`). It turns off the heritage records, findings and scan coverage overlays, which would sit on the very feature the card describes, and a toast says how to turn them back on. The button's words name the example, so its name is what it shows. One pair is two kinds of earthwork rather than an earthwork and a look-alike: an example with a feature class in place of an explanation is tagged as an earthwork. A picture whose contrast was stretched says so on its card. The ladder's weights aren't in `/meta`, so the guide says only that a trusted regular or an archaeologist counts for more. The about page says what OpenAntiquity is, who runs it, that it is free and non-commercial, how sites are protected, who may contribute, and why there are no private messages. Its credits list every source the API names, grouped and searchable (`creditList.ts`): the map's layers, one entry per attribution and licence, the record sources in `/meta` by category, and the services the browser asks itself from `GET /context/live-sources`, asked for separately so the rest shows at once. The notices are pages at `/about/:notice`: `terms`, `privacy`, `reporting` and `takedown`, each marked as a draft at the top and written in `notices.tsx` from what the code stores and does. A link to `/about#terms`, the default `terms.url` in `/meta` that the welcome sheet opens in a new tab, or to any notice that way, is replaced by that notice's own page. The terms and the privacy notice open with five lines "In short", with the detail in closed sections below. The minimum age and the age bands come from `auth.age_bands`, the sign-in providers named from the enabled ones in `auth.providers`, and the licence from `app.contribution_licence`, linked only where `about/facts.ts` knows its address. `/meta` doesn't send the contact address (`FIELDCLUB_CONTACT`), so the about page says once that one will be given, and the notices point to it, until `app.contact` appears.
